# Developing Softwarden

How to run Softwarden from source, what each part of the repository does, the data and UI rules a change follows, and
reference notes on each feature. The [README](../README.md) is the short introduction; [INSTALL.md](INSTALL.md)
installs it on a server and [TOUR.md](TOUR.md) walks through the product with the demo data.

## Run it locally

Needs Docker, [uv](https://docs.astral.sh/uv/) (Python 3.13), and Node 22.

```bash
docker compose -f compose.yaml -f compose.dev.yaml up -d db   # Postgres 17 on 127.0.0.1:5434, password softwarden-dev
cd apps/api
export SOFTWARDEN_DEBUG=1                    # development mode (off by default): dev secret key, simulators
uv sync
uv run python manage.py migrate
uv run python manage.py seed_demo            # synthetic Contoso organization and demo accounts
uv run python manage.py runserver 127.0.0.1:8010
```

`SOFTWARDEN_DEBUG` is off unless set, so every `manage.py` command on your machine needs `SOFTWARDEN_DEBUG=1` in its terminal (PowerShell: `$env:SOFTWARDEN_DEBUG = "1"`); without it the API refuses to start on the development secret key ("Set SOFTWARDEN_SECRET_KEY"). `pytest` and `mypy` turn it on themselves (`apps/api/tests/settings.py`). Never set it on a server; the image sets it to `0`.

The daily digest is built by a separate worker; run it in another terminal if you want digests locally (Needs attention works without it):

```bash
cd apps/api && SOFTWARDEN_DEBUG=1 uv run python manage.py run_worker      # one tick a minute; --once for a single tick
```

In a second terminal:

```bash
cd apps/web
npm install
npm run dev                                  # http://localhost:5173 (proxies /api to :8010)
```

`seed_demo` makes the Contoso organization, its accounts, a dependency scenario, a renewal scenario, a discovery scenario an AI agents scenario (three providers, four models and three agents: a complete Copilot Studio HR assistant, one without a human-in-loop decision and one without an owner) and five custom fields (Business case, Annual cost (EUR), SOX scope, Hosting regions and Certificate expiry, a reminder source; none required) with values on the HR assistant, Workday HR, Finance Ledger and Nightly Payroll Export, and two data-quality exceptions (no vendor and no documentation marked not applicable on the first records failing them), with audit history. It is safe to run again (it leaves an organization that already has records, renewals or AI providers alone); `seed_demo --accounts-only` makes only the accounts, people, teams and vendors, which is what the Playwright suite starts from. To rebuild the demo from scratch, stop the API, run `DROP DATABASE softwarden; CREATE DATABASE softwarden;` in `psql`, then `migrate` and `seed_demo`.

`compose.dev.yaml` gives the database the fixed development password `softwarden-dev`, which `settings.py` uses when nothing else is set. It also keeps the dev stack's data in its own volumes (`softwarden-dev-db`, `softwarden-dev-secrets` and the rest), so the plain stack (`docker compose up`, with its generated password) and the dev stack never share a database. You can switch between them without `down -v`. The dev stack starts on its own empty database volume: run `migrate` and `seed_demo` once. A dev database made by an earlier version, which shared the plain stack's volume, stays in the `softwarden-db` volume, untouched.

### The REST API

Everything the SPA does goes through `/api/v1/`, described at `GET /api/v1/schema?format=json` (OpenAPI; any signed-in account). Scripts use an API token (`Authorization: Bearer sw_...`, created in Administration › API tokens; [docs/API.md](API.md#signing-in) explains them); the SPA uses its session cookie plus the `X-CSRFToken` header on writes.

- **Roles.** Every route declares its minimum role: Viewer reads, Editor writes, Admin deletes records and runs administration; a few routes are public (sign-in, setup, health). A token acts with its owner's role in its own organization, and a **read-only token gets 403 `This token is read-only.` on any write to a signed-in route** (POST, PATCH, PUT or DELETE), before the role check. Public routes such as sign-in don't refuse it, and a method a route doesn't have answers 405 first. A role refusal is a 403 problem naming the role; an edition without a feature's capability is a 403 problem naming the capability.
- **Errors** are RFC 9457 problem details (`application/problem+json`) with `type`, `title`, `status`, `detail` and, for field problems, `errors` keyed by field or query parameter. Another organization's record is a 404, the same as one that doesn't exist. Every error is one, on every route (an unknown path under `/api/`, a CSRF failure, an oversize body, an unhandled exception, which never carries the exception's text), and `type` always names a documented problem (`/problems/invalid-request`, `/problems/read-only-token`, `/problems/rate-limited`, ...): [docs/API.md](API.md) lists them.
- **Rate limits.** Every signed-in request counts against one bucket: the API token's own when it carries one, else the user's, so one script exhausting its token never slows the same person's other tokens or their browser. Reads and writes count apart: `SOFTWARDEN_API_READ_RATE` (default `1200/min`) and `SOFTWARDEN_API_WRITE_RATE` (default `240/min`), counted in the database so the limit holds across every process and pod; empty turns a limit off. Over it: `429 /problems/rate-limited` with `Retry-After`. The search, upload, sign-in, setup and calendar-feed limits apply on top, and failed sign-ins are also slowed per account (docs/API.md "Rate limits").
- **Timestamps** are RFC 3339 in UTC with `Z` (`2026-11-07T08:00:00Z`) on every serializer (accounts, tokens, imports, connections and contracts wrote `+00:00` before).
- **Generated client.** `cd apps/web && npm run api:types` writes TypeScript types for the whole API (openapi-typescript) to `src/generated/openapi.d.ts`; the API gate generates and compiles them on every run (`tests/test_typescript_client.py`). The file is committed and the SPA uses it (`src/lib/openapi.ts`: webhooks, the webhook log and API tokens); `npm run lint` fails when it is stale (`npm run api:check`; skipped without `uv`), and CI's `api` job runs `npm run api:check` with `SOFTWARDEN_API_TYPES_CHECK=required`, so run `npm run api:types` after a schema change. See [docs/API.md](API.md) for authentication, problem types, rate limits, ETags, pagination and what each model's API covers.
- **Lists.** Applications, components, AI agents and integrations return pages: `{"results": [...], "next": "...", "previous": "..."}`. Pass `next` or `previous` back as `?cursor=`; `page_size` is 50 by default and at most 200. A cursor only works with the ordering it came from. Shorter lists (people, teams, departments, vendors, software categories, AI providers, AI models, tags, relationships (`?limit=1..500` instead returns `{"results", "count", "has_more"}`: the first links in the list's order and how many match), reviews, instances, assessments, renewals, the digest log, connectors and their runs, a record's discovery sources, import sources, import runs, API tokens and users) return a plain array. The audit log and each record's History (`/audit-events`, `/applications/<id>/audit` and the same for components, AI agents, integrations and renewals) are newest first, 50 at a time, as `{"results": [...], "next": "<event id>"}` (`?cursor=`); discovery candidates are `{"status", "counts", "results", "next"}`, 50 at a time by source name with `next` an offset; an import run's rows are `{"count", "results"}` with `offset` and `limit` (200 by default, at most 1,000). `ordering` takes one or more of the list's fields, comma-separated, `-` for descending (applications, components and AI agents: `name`, `lifecycle`, `criticality`, `created_at`, `updated_at`, and for agents `risk_classification`, from unacceptable to minimal; integrations the same without `criticality`; each list's choices are in the OpenAPI description); without it records are by relevance when searching, then name. Renewals are always by action deadline, then name.
- **Filters** are query parameters, all combinable: applications, components and AI agents take `q` (search), `lifecycle` (comma-separated), `criticality`, `owner` (business or technical, a Person ID), `support_team`, `it_steward`, `gap`, `review_state`, `archived` (`false` by default, `true` or `all`), `imported`, `tag`, `department`, `data_classification` (comma-separated), plus `vendor`, `category`, `deployment_model`, `authentication_method` (comma-separated), `sso_enabled` and `scim_provisioning` (`true`, `false` or `unknown`) for applications, or `component_type`, `hosting` and `environment` for components, or `platform`, `channel` (any of the listed channels), `risk_classification`, `auth_mode`, `environment` (all comma-separated), `human_in_loop` and `actions_can_write` (`true`, `false` or `unknown`), `model` and `provider` (IDs) for AI agents; with the compliance profile on (below) also `is_gxp`, `validation_status`, `risk_tier` and `periodic_review_due` (a field error while it is off). Integrations take `q`, `lifecycle`, `owner` (technical), `support_team`, `it_steward`, `archived`, `source`, `target`, `protocol`, `implemented`, and `direction`, `auth_method`, `data_classification` and `data_category` (each comma-separated); relationships `resource` and `type`; people `active`; assessments `status`, `change_type`, `stale`, `owner`, `target` and `q`; AI models `provider`, `modality` (comma-separated), `hosting_region` (ignoring case), `in_use` and `q`; renewals `q`, `auto_renew`, `followup`, `decision`, `due_within`, `overdue`, `has_gaps`, `mine`, `application` and `archived`; the digest log `status` and `for_date`; the audit log `actor` (user ID), `action` (an action or a group such as `relationship`), `from` and `to` (dates in the organization's timezone, inclusive), `target_type` (such as `Resource` or `RenewalCycle`; the page lists them as `target_types`), `target` and `related_target` (IDs: `related_target=<application id>` finds its instance and review events) and `request_id`; discovery candidates `status` (`candidates` by default, `new`, `changed`, `linked`, `dismissed`, `gone` or `all`), `connector` and `q`; import sources `kind`; import runs `kind` and `status`; an import run's rows `outcome` and `q`; users `role` and `active`. An unknown parameter or a bad value is a 400 that names it; a filter naming another organization's record is a 404. CSV export (`/applications/export.csv`, `/components/export.csv`, `/ai-agents/export.csv`), Excel export (the same with `.xlsx`) and saved filters validate their query the same way as the list.
- **Catalog fields.** Applications carry `category` (a software category; `/categories` lists the organization's, seeded with a default list and edited by Editors and Admins), `deployment_model`, `version`, `primary_url`, `admin_url`, `authentication_method`, `sso_enabled` and `scim_provisioning` (true, false or null for not recorded), `entra_app_id` and `service_principal_id` (GUIDs); components `hosting`, `environment`, `runbook_url`, `schedule_or_trigger`, `azure_resource_id`, `pp_environment_id` and `external_id`, and the component types `api`, `service`, `workflow` and `infra_automation` join the existing ones; both kinds `department`, `cost_center` and `data_classification`. Vendors add `support_url`, `support_email`, `support_phone`, `portal_url`, `account_manager` (a Person) and `notes`; teams have optional `members` (Person IDs in, people out); tags a `color` (a palette name: gray, blue, teal, green, amber, orange, red, violet, magenta) and a `description`, set with `PATCH /tags/<id>` (Editor). Every existing response key is unchanged.
- **AI agents.** `/ai-agents` is a record kind like applications and components (list, detail, create, PATCH, archive, restore, Admin delete, `/reviews`, `/audit`, `/discovery-sources`, CSV and Excel export; CSV import of agents comes later, so there is no `template.csv`). An agent has the shared record fields plus `platform`, `models_used` (AI model IDs in, `{id, name, version, provider}` out; replaced as a whole), `environment`, `pp_environment_id`, `channels` (a list: `teams`, `m365_copilot`, `web`, `api`, `email`, `other`), `knowledge_sources`, `tools_connectors`, `auth_mode`, `run_as_identity`, `data_access_scope`, `human_in_loop` and `actions_can_write` (true, false or null for not recorded), `risk_classification`, `repo_url`, `external_id` and `purpose`; its `gaps` add "No data access scope" and "No human-in-loop decision". Agents can depend on (and replace) records; integration ends stay applications and components. `/ai-providers` (`name`, `website`) and `/ai-models` (`provider`, `name`, `version`, `modality`, `hosting_region`) are read by any role and written by Editors and Admins; `usage` counts a provider's models and a model's agents, and deleting either while used is a 409 naming what uses it. `GET /ai-models/in-use` (any role) is the models-in-use report: each model unarchived agents use, with `agents` and `live_agents` (Active or Deprecated), most used first. Needs attention has an `agent_gaps` queue (live agents with no owner, no data access scope or no human-in-loop decision), snoozed like the others and in the daily digest as "AI agent gaps"; agents also appear under ownership gaps and reviews.
- **Compliance profile.** Off by default; an organization's Admin turns it on with `PATCH /organization` `{"compliance_profile_enabled": true}` (without the `compliance_profile` capability that is a 403 capability problem). While it is on, applications, components and AI agents carry `is_gxp`, `validation_status`, `validation_doc_url`, `last_periodic_review`, `next_periodic_review` and `risk_tier`, the CSV template and both exports gain those columns, and the filters above work; while it is off the keys are absent from responses (not null), from the audit log and History (including events recorded while it was on) and a write naming one is a field error. Turning it off keeps the values; turning it back on shows them, and their history, again.
- **Excel export.** `export.xlsx` takes the CSV export's parameters and holds its rows and columns plus `review_state`, `next_review_date` and `updated_at`, in a workbook with a bold, frozen header row and a filter. Dates are dates and yes/no fields booleans; text cells get the CSV export's formula escape and are stored as text, never formulas. A second sheet, Custom fields, describes the custom field columns (below) when the kind has any. Further sheets come from `imports/xlsxio.EXTRA_SHEETS`. Written with openpyxl on the server; audited as `export` with `format: xlsx`.
- **Custom fields.** Admins define fields at `/custom-fields` (every role reads them; the `custom_fields` capability, in every edition): `name` (lowercase letters, digits and single underscores; unique; never changes), `label` (unique, changeable), `type` (`text` up to 500 characters on one line, `longtext` up to 5,000, `integer` (±2^53), `decimal` (at most 15 digits, 6 after the point), `boolean`, `date` (YYYY-MM-DD), `url` (http or https, up to 2,000), `select`, `multiselect`, `object` (a JSON object, at most 5 levels and 5,000 characters, no secret-looking keys)), `choices` (choice types; no commas or semicolons), `required`, `default`, `applies_to` (any of `application`, `component`, `integration`, `ai_agent`, `vendor`), `weight` (lower first), `description` and `is_reminder_source` (date fields; reminders). `usage` counts the records and vendors holding a value. A field's type can't change while a value exists, a choice in use can't be removed and a kind can't leave `applies_to` while records of that kind hold values (each a field error saying how many); deleting a field removes its values everywhere and is audited once with the count. Records, integrations and vendors return `custom_field_data` (every field that applies, in weight order, null when unset) and take it on POST and PATCH: only the names sent change, null or `""` clears one, defaults fill a new record, and an unknown name, a field that doesn't apply, a bad value or a missing required value is a field error keyed `custom_field_data.<name>`. Lists (and exports and saved filters) take `cf_<name>`: text, long text and URL contain (ignoring case), choices take comma-separated values (any of), yes/no `true` or `false`, numbers and dates an exact value plus `cf_<name>__gte` and `cf_<name>__lte`; every field also `cf_<name>__set=true|false`, which is all an object field takes. CSV export, the template and Excel export add a `cf_<name>` column per field (multiple choices separated by `;`, objects as JSON); CSV import reads those columns with the same checks, row by row, and a mapped file can map any heading to a custom field (suggested by label). Snapshots, History and the audit log show each value as `custom_field_data.<name>` with the field's current label.
- **Attachments.** Files and links on applications, components, AI agents, integrations and vendors (the `attachments` capability, in every edition). `GET /<applications|components|ai-agents|integrations|vendors>/<id>/attachments` lists them (any role; a plain array by category then title; filters `kind`, `category`). `POST` to the same path adds one (Editor, Admin): `multipart/form-data` with `file` (and optional `title`, `category`) uploads a file, a JSON body `{"url": "https://...", "title": ..., "category": ...}` adds a link (http or https only, no user name or password in it; other keys are refused). Categories: `contract`, `invoice`, `sop_runbook`, `architecture`, `validation`, `vendor_docs`, `security_review`, `other` (default). `GET`, `PATCH` (title, category, a link's `url`) and `DELETE /attachments/<id>` (Editor, Admin for writes); `GET /attachments/<id>/download` (any role) streams the file, always as `Content-Disposition: attachment` with the cleaned original name (RFC 6266 / 5987), the type the content check found, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` and `Cache-Control: private, no-store`; nothing is ever shown inline. Attachment IDs are random UUIDs and another organization's is the same 404 as one that doesn't exist. A file's extension must be allowed and its content must match it (PDF, Office Open XML and legacy Office, PNG, JPEG, GIF, ZIP, UTF-8 text for txt, csv, md and json); the browser's content type is ignored, and HTML, SVG, scripts and programs can't be allowed at all. Limits: `SOFTWARDEN_ATTACHMENT_MAX_MB` (25), `SOFTWARDEN_ATTACHMENT_EXTENSIONS` (pdf, docx, xlsx, pptx, vsdx, doc, xls, png, jpg, jpeg, gif, txt, csv, md, json, zip) and `SOFTWARDEN_ATTACHMENT_QUOTA_MB` per organization (10240; 0 for none); an Admin can tighten each for the organization with `PATCH /organization` `attachment_max_size_mb`, `attachment_extensions`, `attachment_quota_mb` (null goes back to the installation's), and `GET /organization` shows them under `attachments` with the space used and `retention_days` (how long a removed file is kept). File uploads are limited to `SOFTWARDEN_ATTACHMENT_UPLOAD_RATE` per user (60/hour; 429 with `Retry-After`). Any multipart request, on any path, over `SOFTWARDEN_MAX_REQUEST_MB` MiB (default the attachment limit plus 1, at least 6) is refused with 413 before its body is read, and one without a Content-Length with 411; in Compose, Caddy's `request_body` limit uses the same variable, also in MiB (26 by default), and a start-up check (`softwarden.E105`) refuses a request limit smaller than the attachment limit. Every write is audited (`attachment.created`, `.updated`, `.deleted`) with the record or vendor as related target, so it shows in the record's History; snapshots hold the title, category, link, file name, type, size and SHA-256, never the content or where it is stored. Deleting an attachment (or its record or vendor) keeps the file for `SOFTWARDEN_ATTACHMENT_RETENTION_DAYS` (7) and the nightly `attachments.sweep` schedule then deletes it, and any stored file no row references; `manage.py sweep_attachments` runs it now and `manage.py verify_attachments [--organization <slug>]` checks every file's size and SHA-256 (non-zero exit on a problem). Files live in `SOFTWARDEN_MEDIA_ROOT` (`apps/api/media` locally, the `softwarden-media` volume at `/data/media` in Docker).
- **In the SPA.** Applications, components, AI agents and integrations have an **Attachments** tab, and each vendor row on the Vendors page (`/vendors`; `/admin/people?tab=vendors` redirects there) an **Attachments** button (a dialog, `/vendors?attachments=<vendor id>`): files and links grouped by category, Download (a plain link to the download URL) or Open link, and for Editors and Admins Upload file (title, category, a progress bar; the organization's size, type and quota limits are checked before anything is sent, and the API's 413, 429 and field errors are shown), Add link, Edit (If-Match) and Remove (which names the retention window). The command palette searches through `GET /search` (records, vendors, people, attachments, with snippets) plus renewals by name, and its **Search everything for …** opens `/search?q=&kinds=&include_archived=&limit=` (grouped by kind with counts, Show all N, close matches and ignored words said so). **Dashboard** (`/dashboard`) has the Data quality panel (compliance, complete records, failing records by check as a chart and a table, by kind); **Data quality** (`/data-quality`) has Failing records (`?rule=&kind=&it_steward=`), Checks and Exceptions (`?tab=exceptions&status=&owner=left&record=`) with add, change (extend-only, If-Match) and remove. Record lists show a Completeness column (sortable) and take Completeness below / at least and Failing check filters; a record's Overview shows its checks as chips with Add exception. Organization settings has the attachment limits and a switch per data-quality check.
- **Global search.** `GET /search?q=...` (any role) searches applications, components, integrations, AI agents, vendors, people and attachments at once and returns `{"query", "fuzzy", "groups": [{"kind", "count", "results": [...]}]}`, a group per kind searched, best match first. Every word must match (anywhere: a record's name, description, purpose, vendor's name, tags, AI models and providers, text-like custom fields, other text); the last word is a prefix, even a single letter, so `contoso pay` finds Contoso's Payroll. `q` is normalized to Unicode NFC; a word with nothing searchable in it (a lone `²`) is left out and listed in the response's `ignored`, and a `q` with no searchable word is a 400. People match by name only (never an anonymized person); attachments by title and file name, with their `parent`. A result has `id`, `kind`, `name`, `path` (its route under `/api/v1/`, e.g. `vendors/<id>`), `score`, `archived`, `lifecycle` and a `snippet` `{"field", "label", "segments": [{"text", "match"}]}`: plain text segments to render as text, never HTML. Parameters: `kinds` (comma-separated; default every kind the edition has, and naming `ai_agent` or `attachment` without its capability is a 403 capability problem), `limit` per kind (1 to 100, default 10; `count` is every match), `include_archived` (default false; archived records, inactive people, attachments on archived records). When nothing matches every word, names similar to the query come back with `"fuzzy": true` (typos). Searches are rate-limited per user (`SOFTWARDEN_SEARCH_RATE`, default `600/min`; empty turns it off): 429 with `Retry-After`. Contracts (kind `contract`) match on their name, contract and PO numbers, notes, cost center, vendor's name and text custom fields. The list routes' own `q` filters are unchanged.
- **Data quality.** Built-in checks on applications, components and AI agents (the `data_quality` capability, in every edition; `catalog/quality.py`). Each rule is plain data (kinds, severity, an `applies` and a `fails` condition over named fields) so custom rules and rule packs can use the same shape later: no business owner, no technical owner, no support team, inactive owner, no criticality, no data classification, no documentation (no documentation or runbook URL and no SOP, architecture or vendor documentation attachment), no vendor (applications not built in-house), not on a contract (applications not built in-house and not free, open source or internal-licensed, with no line on a live or signed contract that isn't archived; needs `contracts`), review overdue (active and deprecated records; never reviewed counts from one review interval after creation), and for AI agents no data access scope and no human-in-loop decision (agents need `ai_agents`); with the compliance profile on also no validation status, no risk tier, no periodic review date (GxP or high risk) and periodic review overdue. The ownership, agent and review checks use the same wording as the record's `gaps`, which are unchanged. `GET /data-quality/rules` (any role) lists every rule with its `status` (`on`, `off`, `unavailable` and why), its `spec` and, while on, how many live records (not archived, not retired) pass, fail and are excepted; `GET /data-quality/summary` gives the compliance percentage (passing checks over passing plus failing, excepted ones left out), the records failing nothing, and the same by kind and by rule (the dashboard's Data quality panel); `GET /data-quality/failures?rule=&kind=&it_steward=` pages through live records failing a rule (or any), each with its results. Record lists and pages carry `quality`: `score` (completeness 0 to 100, rounded down; 100 when nothing applies), `failing` and `excepted` checks (id, label, severity). The record lists take `completeness__lt`, `completeness__gte`, `quality_rule` (records failing it) and `ordering=completeness`. An Admin turns rules off with `PATCH /organization` `data_quality_disabled_rules` (a list of ids; the gap checks can't be turned off). An Editor marks a check not applicable to one record with `POST /data-quality/exceptions` `{"record", "rule", "reason", "owner", "expires_on"}`: only documentation, vendor, contract and periodic review date take one; a reason and an active accountable person are required, and it lasts until `expires_on` (today to a year ahead, a year by default), after which the check counts again (`active: false`; extend it with `PATCH`, never shorten it, and only with an active owner). `GET`, `PATCH` (reason, owner, a later expiry) and `DELETE /data-quality/exceptions/<id>`; filters `rule`, `record`, `owner`, `owner_active` (`false`: owners who left or were anonymized), `active`. Blank text (a data access scope) means whitespace by Python's definition, no-break spaces included. Exceptions are audited on the record (`quality_exception.created`, `.updated`, `.deleted`) and go with it when it is deleted. Needs attention gains a **Data quality** queue: one row per rule and IT steward with live active or deprecated records failing it (`count`, `it_steward`), routed to that steward, and snoozable like the others; the ownership, agent and review checks stay in their own queues, so nothing is listed twice. It counts in `counts` (the navigation badge) and has its own section in the daily digest, each line linking to `/data-quality?rule=<id>&it_steward=<user id or none>`.
- **Integration fields.** Integrations carry `direction` (`one_way`, `two_way`), `auth_method` (`oauth`, `api_key`, `basic`, `certificate`, `managed_identity`, `ssh_key`, `none`, `other`), `monitoring_url` (http or https, up to 2,000 characters), `data_classification` and `data_categories` alongside `protocol`, `schedule` and `data_purpose`; each is `""` (`data_categories` `[]`) when not recorded and filterable (comma-separated) except the URL.
- **Dependencies and map.** `GET /<applications|components|ai-agents>/<id>/dependencies` (any role) is the dependency explorer with that record as the target: the same parameters and body as `GET /dependencies?target=<id>` (`direction` dependents (default), depends_on or both; `depth` 1 to 10 or `all`; `include_retired`; `show_instances`; `data_flows`). Traversal follows every relationship type with `is_dependency`. Links that close a loop are rows with `cycle: true` and are also listed in `cycles` (relationship, ends, the record it leads back to). Data flows carry `direction` and `auth_method`. `GET /<applications|components|ai-agents>/<id>/map?depth=1|2` (any role, default 1) returns everything the record is connected to (relationships both ways, integrations as edges, instances, linked discovery sources, the contracts the record is on and an application's license pools) as `nodes`, `edges` and table `rows` grouped by `categories`; archived and retired nodes are flagged, at most 150 nodes (`truncated`). Another organization's record, or a record of another kind under the route, is a 404.
- **Contracts and license pools.** The `contracts` capability (every edition). `GET /contracts` (any role; keyset pages; unarchived by default, `archived=true|all`) with filters `q` (name, contract or PO number, vendor), `vendor`, `status` and `billing_frequency` (comma-separated), `auto_renew`, `cost_center`, `currency`, `end_before` / `end_after`, `deadline_before` / `deadline_after`, `renewal_obligation` (an id or `none`), `record` (contracts with a line for it) and `cf_<name>`; `ordering` name, `ends_on`, `deadline_on` (none last), created_at, updated_at. `POST /contracts`, `PATCH`, `DELETE` (Admin; refused while a license pool or next term points at it), `POST .../archive` and `.../restore`. Money is a string with two places next to a three-letter `currency`; `annualized_cost` (with `annualization_note`) and `cancellation_deadline` (with `deadline`: date, label Calculated / Assumed / Renewal action, explanation, timing) are worked out, never sent; `GET /contracts/preview?amount=&billing_frequency=&start_date=&end_date=&auto_renew=&notice_value=&notice_unit=` returns them for a form. Billing frequencies: monthly, quarterly, semiannual, annual, multi_year (the whole term's amount, spread over the term's months from the dates), one_time, usage_based. A contract links a renewal with `renewal_obligation` (an id) or creates one with `create_renewal_obligation: true`; the renewal's open cycle then takes the contract's end date, notice period and auto-renewal, and the renewal refuses to change them itself, so its reminders and the contract's deadline never disagree (`GET /renewals/<id>` shows the `contract`). Lines: `GET`/`POST /contracts/<id>/lines` (`record`, `allocation_percent`; fixed shares sum to at most 100%), `GET`/`PATCH`/`DELETE /contracts/<id>/lines/<line id>` (Editor); the contract's detail lists them with `share_percent` and `annual_amount` (to the cent, summing exactly), `allocated_percent`, `unallocated` and its `license_pools`. `GET /contracts/export.csv` and `export.xlsx` (any role; the list's filters; lines as `Name=40; Name`; audited as `export`). `GET /contracts/<id>/attachments` and `/audit` (its lines and attachments in words). `GET /license-pools` (filters `q`, `application`, `contract`, `seat_sync`, `overused`, `cf_<name>`), `POST`, `GET`/`PATCH`/`DELETE /license-pools/<id>` (Admin deletes), `/audit`: seats assigned may exceed seats purchased (`overused`, `utilization` over 100); `seat_sync` needs a SKU ID and only one pool per SKU may sync. Custom fields apply to `contract` and `license_pool`; contracts and pools appear on a record's Map.
- **Renewing contracts and license seats.** `GET /contracts/<id>/renew` (any role) says whether the contract can be decided now (`can_renew`, `refusal`), the renewal and open cycle the decision is recorded on, and the next term's `defaults` (starts the day after it ends, as long, the same money, notice, auto-renewal, every line and pool). `POST /contracts/<id>/renew` (Editor; If-Match takes the contract's ETag) with `decision` `renew`, `renegotiate` or `cancel`, `decision_notes` (required to cancel), `decided_on`, `completion_evidence` and, renewing, any next-term field (`name`, `contract_number`, `po_number`, `amount`, `currency`, `billing_frequency`, `start_date`, `end_date`, `auto_renew`, `notice_value`/`notice_unit`, `notes`), `lines` and `pools` (IDs to carry; default all), `pool_action` (`move`, default, or `copy`) and `overlap_confirmed`. In one transaction it records the decision with the money and dates before and after (`terms_change`) on the linked renewal's open cycle and completes it; renewing creates the next term (`predecessor` set, linked to the same renewal, which it then drives, Signed until it starts), copies the lines, moves the pools and establishes the renewal's next cycle with the next term's dates (201 with the next term); canceling sets the contract to Canceled (200). Refused (409) for an archived contract, one that is canceled, expired or renewed, one that already has a next term (two renews at once: one wins), an archived renewal or one driven by an unrelated contract, and renewing without an end date; a next term that doesn't end after this one, or starts before it ends without `overlap_confirmed`, is a field error. The next term's History says "renewed from". A contract's detail now carries its `renewal` (as `GET /renewals/<id>`, with every cycle and `terms_change`). `GET /license-pools/totals` (any role) adds seats up per application and SKU and for the organization (purchased, assigned, available, utilization, overuse). `GET /license-pools/seat-review?status=open|dismissed|all&pool=` (any role) lists **proposed seat counts**: pools whose SKU ID a license observation (discovery kind `license`, written by the Entra licenses source) reports with other purchased or assigned seats, plus `unbound` SKUs no pool has; `POST /license-pools/<id>/seat-review/<observation id>/apply` (Editor; optional `counts`) is an ordinary audited pool edit, and `.../dismiss` (Editor; `reason`) is recorded until the source's counts change. A pool with `seat_sync` is overwritten by the sync path instead, which alone sets `last_synced`. Pools with open proposals are a Needs attention queue, `seat_counts`, counted in the badge and sent in the digest. Contract statuses follow their dates: the hourly `contracts.advance_terms` schedule (on the System page) makes a Signed term Active on its start date and, once a term's end date has passed (organization time), Renewed when a next term (not canceled or archived) renews it or Expired when none does and it doesn't auto-renew (a Renewed term whose next term stops counting becomes Expired, never Active again on its own); each change is audited and the renewal re-synced.
- **Dashboard and reports.** `GET /dashboard` (any role) returns every dashboard block at once: `needs_attention` (the badge counts and each queue's size per scope, from the same function as Needs attention), `deadlines` (action deadlines due within 30, 60 and 90 days and overdue, with the first 10 rows), `expiring_credentials` (API tokens expiring within 30 days or expired in the last 30; an Admin sees the organization's; others their own; adds discovered credentials), `spend` (per currency: `totals` and the largest 8 groups by vendor, department and category, every named gap, and one "Everything else" row for the other groups), `license_utilization` and `data_quality` (as `GET /data-quality/summary`); a block the edition lacks is null. `GET /reports/spend?by=vendor|department|category|cost_center` (any role, `contracts`) is the annualized cost of live contracts (Active, Pending renewal; not archived) split over their lines to the cent, grouped per currency (never converted), with `totals` (run rate, one-time, `annualized`, and Signed terms not started yet as `future`) and the `allocations` detail; every dimension adds up to the same total. Cost center is the line's record's, else the contract's; cost not on a record is the `unallocated` gap; other gaps are named (`no_vendor`, `no_department`, `no_category`, `not_application`, `no_cost_center`). `GET /reports/renewals-calendar?months=1..24` (any role; default 12, this month first) lists every open action deadline to the end of the window, overdue ones included: a renewal's open cycle (with the contract that drives it) and contracts that drive no renewal and that no next term renews (a renewed or renegotiated term has no action left), from the same dates reminders use. CSV exports, formula-escaped and audited as `export`: `GET /reports/spend/export.csv?by=`, `/reports/renewals-calendar/export.csv?months=`, `/reports/license-utilization/export.csv`. **Calendar feed:** `GET /calendar-feed` (your feed: `active`, `prefix`, `last_used_at`), `POST /calendar-feed` (create; 409 while you have one), `POST /calendar-feed/rotate` (a new address, the old one stops at once) and `DELETE /calendar-feed` (revoke), any role from a signed-in session (API tokens are refused). Create and rotate return the subscription `url` (https; no `webcal://` link, which calendar apps fetch over plain http first) once; only a hash of the secret is kept. Subscribe to it in Outlook (Add calendar, Subscribe from web), Google Calendar (From URL) or Apple Calendar. The feed, `GET /calendar/renewals.ics?token=...&months=`, is public and authenticated only by that secret: an RFC 5545 calendar with one all-day event per deadline and a stable UID, served as `text/calendar`; anything else, a revoked feed or one whose owner left the organization included, is the same 404 (removing a member revokes their feed there, audited). It is rate limited, in the database like the other throttles, per feed (`SOFTWARDEN_CALENDAR_FEED_RATE`, default `60/hour`) and per client address (`SOFTWARDEN_CALENDAR_FEED_ADDRESS_RATE`, `1200/hour`; Outlook.com and Google fetch from shared addresses); empty turns a limit off. The secret is in the query string because gunicorn's access log writes paths only; if you add access logging to Caddy or another proxy, leave the query string out.
- **Importing contracts and license pools.** `POST /imports` takes `kind` `contract` or `license_pool` (also `contracts`, `licence-pools`; the `contracts` capability), and `GET /imports/template.csv?kind=contract|license_pool` gives the headings. Contract columns: `softwarden_id`, `external_key`, `name`, `vendor` (by name; unknown ones are offered for Create or Leave gap), `contract_number`, `po_number`, `amount`, `currency`, `billing_frequency`, `annualized_cost` (ignored), `start_date`, `end_date` (YYYY-MM-DD), `auto_renew`, `notice_value`, `notice_unit` (days when blank), `cancellation_deadline` (ignored), `renewal_owner_email`, `renewal_owner_name`, `status`, `cost_center`, `renewal` (an existing renewal by name or ID), `create_renewal_obligation` (true to create one), `items` and `notes`, plus `cf_<name>`. `items` is "Microsoft 365=70; Entra ID=30" or "Jira=60; Confluence" (a line without `=` shares what the fixed percentages leave); write `application:`, `component:` or `agent:` before a name that more than one kind uses, or a record's ID. License pool columns: `softwarden_id`, `external_key`, `application`, `contract` (number, name or ID), `sku_name`, `sku_id`, `seats_purchased`, `seats_assigned`, `seat_sync` (needs a SKU ID; one syncing pool per SKU), `last_synced` (ignored: only discovery sets it), `notes`, `cf_<name>`. Rows match by Softwarden ID, the source's external key, then the contract number (contracts) or application and SKU name (pools); a contract with the same name and no number is a Possible match to decide. For files of up to 500 rows the preview rehearses each row through the contract services and rolls it back (larger files say so in `panels.notices` and are checked at commit), so the services' refusals (fixed shares over 100 %, a renewal another contract drives, a renewal without an end date, a second syncing pool for a SKU) are row errors, and each row shows its annualized cost, cancellation deadline (with its label) and how the cost splits over its lines (`computed`). The commit writes through the same services, audited with the import run. `GET /contracts/export.csv` and `GET /license-pools/export.csv` (any role) write the same columns, custom fields included, and re-import with every row Unchanged. `tests/fixtures/demo_contracts.csv` is an earlier version's demo contracts with fixed dates (the records it names are in its test); `seed_demo` adds five contracts and two license pools so the dashboard and reports have data.
- **Reminders.** Dated obligations generated from deadlines, never entered by hand (`notify/reminders.py`): renewal action deadlines (each open cycle), contract cancellation deadlines (only for a contract that drives no live renewal: one that drives one is reminded through the renewal, on the same date), periodic reviews (with the compliance profile on), record reviews (the newest review's next review date), custom date fields flagged as reminder sources (contracts and license pools with `contracts`), and discovered credential expiry (feeds it). The dates are the ones the dashboard, the renewals calendar and Needs attention show. The `reminders.generate` schedule runs hourly on each organization's local date (listed on the System page, after `contracts.advance_terms`) and every audited write that can move a date regenerates just that source once its transaction commits; reruns change nothing, a moved date moves an open or snoozed reminder, a source that is gone, archived, completed or switched off closes its reminders as `obsolete`, a source that comes back with the same date brings an obsolete reminder back (acknowledged if it was acknowledged, else open in a new notification cycle), and a resolved reminder is never reopened by the generator. Nothing is sent from here: the notification rules turn reminders into deliveries. `GET /reminders` (any role; keyset pages, soonest first) with filters `status` (open, snoozed, acknowledged, done, obsolete; comma-separated, as of today, so a snooze whose date has passed reads open), `source_type`, `source_id`, `due_after` / `due_before` and `scope` (mine, all, unassigned, routed like Needs attention: a record's IT steward, a renewal's IT follow-up, a contract's renewal owner's user, a pool's application's steward, else the IT coordinator); `GET /reminders/<id>`. Editors and Admins `POST /reminders/<id>/snooze` `{"until": "YYYY-MM-DD"}` (quiet through that date, at most 90 days), `/acknowledge`, `/reopen` and `/resolve` `{"kind": "done|risk_accepted|no_longer_applies", "note", "evidence"}` (a note is required for an accepted risk and for renewal, contract, periodic review and credential reminders); each takes If-Match and is audited (`reminder.snoozed` and so on). Needs attention gains a `reminders` queue (not yet counted in the badge or the digest) for contract, periodic review, custom date and credential reminders due within the largest reminder threshold or overdue; a renewal cycle's reminder rides on its Renewal actions row and a record review's on its Reviews row as `reminder`, so a deadline is never listed twice. Deadline rows (dashboard, calendar) carry the renewal's `cycle`.
- **Composite read endpoints.** Compact, stable answers for scripts and the MCP server, any role, with a session or an API token (read-only tokens included), all `GET` under `/api/v1/composite/`: `search` (GET /search's matching and parameters as one flat list, snippets as plain text; rate limited with it), `deadlines?within_days=90` (every open action deadline up to that many days ahead, overdue ones included, with the 30/60/90-day counts; `within_days` filters the cancel-or-renew-by date, not the term's end, `term_ends`), `renewals?within_days=90` (the same rows, or with `basis=term_end` the open actions whose term ends within that many days or has ended, whatever their deadline, soonest term end first; with who owns each: the renewal owner, the renewal owner of the contract that drives it (`contract_owner`), the IT follow-up, the vendor's account manager and support email, and the covered records with their business and technical owners, IT steward and support team, plus `gaps` naming who is missing), `spend?by=vendor&groups=25` (totals and groups per currency, the rest folded into Everything else), `dependencies?target=<record id>&direction=both&depth=2` (what it relies on, what relies on it, data flows), `discovery-summary` (candidate, missing and differs counts per connector, last and active run), `data-gaps?rule=&kind=` (the data-quality summary and the records failing a check, with owners) and `expiring-credentials?within_days=30&kind=` (API tokens and discovered secrets and certificates, with the linked record's owners). Each body has `count` (every match) and `truncated`; `limit` is 1 to 200 (default 50), except search, whose `limit` is per kind (1 to 100, default 10), spend, which takes `groups` instead, and discovery-summary, which takes no parameters. Every route is GET only: any other method is a 405. They read the same functions as the dashboard, the reports, the explorer and the queues, so the numbers agree. Capabilities as for the screens: renewals or contracts for deadlines and renewals, contracts for spend, data_quality for data gaps (403 problem naming it).
- **Relationship types.** `GET /relationship-types` (any role) lists the organization's types by name: `slug`, `name` (reads from the source, "Depends on"), `inverse_name` (reads from the target, "Is needed by"), `description`, `is_dependency`, `is_core` and `usage` (relationships of that type). Every organization has the core types `depends_on`, `implements` and `replaces`. Admins add more (`POST`, `name` required, `slug` derived from the name when left out), change them (`PATCH`: labels and description of any type, `is_dependency` of an added type; a slug never changes) and delete them (`DELETE`: refused with 409 for a core type and for a type in use, with `blocking_references.relationships` counting the links). An added type takes the same ends as `depends_on`; with `is_dependency` on, the dependency explorer, affected sets, retirement checks and staleness follow it. Relationships still send and receive the slug as `type` (and `?type=` filters by slugs; an unknown slug is a 400) and now also carry `relationship_type` with the labels.
- **OpenAPI names.** A relationship's `type` is a string (a relationship type's slug), so the `RelationshipTypeEnum` component is gone (it was `TypeEnum` in older schemas). A client generated from an earlier schema needs regenerating.
- **ETag and If-Match.** Reading one record (any detail route) returns `ETag: "<revision>"`, a fingerprint of its stored fields (for records also their extension and tags; for renewals also their cycles); writes return the new one. Send it back as `If-Match` on PATCH or DELETE (and on a renewal's cycle edit, with the renewal's ETag) and the change applies only if nobody changed the record since; otherwise the answer is 412 with type `/problems/precondition-failed`, the current `revision` and `ETag`, and nothing is changed. Without `If-Match`, an API token's write applies unconditionally; a signed-in session's write is refused with 428 `/problems/precondition-required` (`SOFTWARDEN_REQUIRE_IF_MATCH`, on by default; docs/ENV.md). End-of-life tracking (`.../end-of-life`) and ticket links (`.../ticket-links/<id>`) take If-Match too. Bulk edit locks the records it changes, so a concurrent If-Match write waits for it rather than racing it. Connectors, import sources, import runs, users (`/users/<id>`) and organization settings (`/organization`) take If-Match the same way. A secret is never part of a revision: a connector's client secret, a token's hash and the license key are left out (replacing a connector's secret still moves its ETag, through the date it was set), as is an import's uploaded file. (The SPA's Undo uses its own check, `expected`, which answers 409 `/problems/stale-value`.)
- **Append-only audit.** Audit events are written by the change they record, in the same transaction. The API reads them (`GET /audit-events`, `/audit-events/<id>`, Admin; each record's `/audit` and `/audit/<event id>`, any role, only that record's events) and has no route that edits or deletes one; the model, its queryset and a database trigger refuse it too. A list row carries `target_type`, `target_id`, `related_target_type`, `related_target_id` (the parent record of an instance, review, link confirmation, renewal cycle or attachment event, whose History shows it; a vendor for a vendor's attachment) and `request_id`; one event read on its own adds `prechange` and `postchange` (the target before and after, references as `{"id", "display"}`) and `diff`, one row per changed field with `change` `added`, `removed` or `changed` and, for tags and covered applications, the entries `added` and `removed` (`diff_source` is `changes` for events written before snapshots). Snapshots hold the audited fields as the API names them, references as `{"id", "display"}` with the name when written (a Person or a User by ID only, `display` null), and never a secret (`catalog/snapshots.py`). A record's `/audit` also lists its children's events (instances, reviews, attachments, data-quality exceptions, the links and integrations it is an end of, a renewal's cycles), each with `child: {kind, kind_label, id, name, sentence}` naming the child in words; `?children=false` keeps the record's own events.
- **Audit log export.** `GET /audit-events/export.csv` (Admin) downloads the log with the list's filters (actor, action, from, to, target_type, target, related_target, request_id), newest first, formula-safe, at most 100,000 events per file (narrow the dates otherwise; more is a 400 of type `/problems/too-many-events` with `count` and `limit`). With `audit.export` (every edition): `GET /audit-events/export.jsonl` gives the same events oldest first as JSON lines for a SIEM, with stable field names (`schema_version` 1) and the before/after snapshots, never a secret. Both are streamed and audited as an `export` event with the filters and the row count requested (written before streaming). Events are cut off by insert time, so a SIEM pulling by date range should overlap its windows and dedupe on `id`.
- **Request IDs.** Every response has an `X-Request-ID` header, and the audit events a request writes carry the same `request_id` (filter the log with `?request_id=`). Behind the Compose proxy it is Caddy's own request UUID (Caddy replaces any `X-Request-ID` a client sends); the app honors the header only from `SOFTWARDEN_TRUSTED_PROXIES` and only if it is a UUID, otherwise it makes one. A worker job's events carry the job's id; a schedule run or a management command gets its own.
- **Write-only secrets.** A connector's client secret is accepted on create and PATCH and never returned (`secret_set_on` says when it was last set); an API token's secret is in its create response only; an invitation's link is in its create or resend response only (the token is stored hashed); a temporary password appears once, in an Admin's reset response. API tokens are managed from a signed-in session only, so a token can't read or revoke tokens.

- **Catalog as code.** The catalog as one YAML file per record, for a git repository whose pull requests review catalog changes (Admin; the `catalog_code` capability, every edition): `GET /catalog-code/export.zip`, `POST /catalog-code/plan` and `POST /catalog-code/apply` (a zip of the tree; apply needs the plan's `plan_hash` and refuses a stale one), or `manage.py catalog_export --org <slug> --dir <path> [--include-people]` and `manage.py catalog_apply --org <slug> --dir <path> [--dry-run] [--prune [--allow-mass-delete]] [--expect-hash <hash> | --no-plan-check]` (a prune that deletes more than 10 records, 20% of a kind, or all of a kind, needs `allow_mass_delete` / `--allow-mass-delete`) (large first loads, over about 2,000 creates, go through the CLI: one API request creates at most 2,000 rows). Format, safety limits and a git workflow: [docs/CATALOG_AS_CODE.md](CATALOG_AS_CODE.md).

### The MCP server

`mcp/` is an MCP server for Claude Desktop and other MCP clients (docs/MCP.md): read tools (`search`, `get_item`, `renewals_with_owners`, `dependencies`, `spend`, `expiring_credentials`, `data_gaps`, `agents_by_model`, `discovery_summary`, `list_reminders`, `list_candidates`) and, only with `MCP_ENABLE_WRITES=1`, If-Match-guarded write tools (`update_record`, `snooze_reminder`, `acknowledge_reminder`, `dismiss_candidate`). It is a thin client of this API with an API token, never the database, so roles, read-only tokens and capabilities apply as for any script. `renewals_with_owners` answers "which contracts renew in the next 90 days and who owns them", asking `composite/renewals?basis=term_end` by default and saying so. IDs must be UUIDs and are percent-encoded in paths; a write's revision must be the exact one read (never `*`).

```bash
cd mcp && uv sync                                  # once
cd mcp && uv run softwarden-mcp                    # stdio, with SOFTWARDEN_URL and SOFTWARDEN_TOKEN (read-only) set
echo SOFTWARDEN_MCP_UPSTREAM=mcp:8001 >> .env      # opt in: Caddy proxies /mcp only while this is set (else 404)
docker compose --profile mcp up -d --build         # streamable HTTP behind Caddy at https://<host>/mcp; each client sends its own Bearer token
```

Claude Desktop's configuration, the HTTP setup, the tool list, the risks of writes and a walk-through with the demo data are in docs/MCP.md. `POST /discovery/observations/<id>/dismiss` takes `If-Match` with the candidate's ETag (412 when it changed since it was read; without the header it is unconditional for an API token, 428 for a signed-in session).

### Backup settings

The worker's nightly backup needs no setup: the image sets `SOFTWARDEN_BACKUP_DIR=/data/backups` (the `softwarden-backups` volume), the init service generates `backup_key` in the secrets volume, and the image carries `postgresql-client-17` and `openssl`. Optional: `SOFTWARDEN_BACKUP_CRON` (`30 2 * * *`, UTC), `SOFTWARDEN_BACKUP_KEEP_DAILY` (14), `SOFTWARDEN_BACKUP_KEEP_WEEKLY` (8), `SOFTWARDEN_BACKUP_STALE_HOURS` (26), `SOFTWARDEN_BACKUP_MIN_FREE_MB` (free space that must remain on the backup disk after a set; unset, the larger of 2 GB and 10 % of the disk: the default volume shares the database's disk, so a run that would go below it is refused and shown on the System page), `SOFTWARDEN_BACKUP_REQUIRE_MOUNT` (1: refuse a destination that isn't a mounted volume, such as `backup_now --inline` in the app container; 0 only for development), and `SOFTWARDEN_BACKUP_KEY_FILE` (a path inside the containers to your own key, mounted into `worker` and `app`; nothing is generated then). Copy the key and the sets off the host (backup runbook). For the host-side alternative below, copy `ops/backup.env.example` to the server and set `BACKUP_DEST` (a mounted share or any path your organization provides) and `BACKUP_KEY_FILE` (a key file that also exists off the host). `BACKUP_KEEP_DAILY` (14) and `BACKUP_KEEP_WEEKLY` (8) are optional. `ops/softwarden-backup.timer` and `.service` run it nightly under systemd. Uploaded import files live in PostgreSQL until the 30-day purge, so the database dump covers them. Attachment files are not in the database: `ops/backup.sh` also archives the `softwarden-media` volume (`/data/media`), encrypted with the same key, and `ops/restore.sh` puts it back and runs `verify_attachments` (backup runbook). The gunicorn request timeout is 120 seconds, so a 5,000-row import commits within one request.

### Preview features (off in 1.0.0)

Okta and Google Workspace discovery, and ServiceNow and Halo ticket connections, are preview features: hidden from
every organization unless the installation sets `SOFTWARDEN_PREVIEW_FEATURES=1` (Compose `.env`, or Helm `extraEnv`;
off by default). With it off, `auth/me` lists none of `preview`, `discovery.okta` and `discovery.google`, whatever
the edition or a platform override says, so the app offers no Okta or Google source, connection tab or setup card and
the ticket connections page offers Jira only. Their routes answer `403 /problems/capability-required`, the schedules
skip them, `GET /discovery/sources` leaves Okta and Google out, and a pasted ServiceNow or Halo address still links
with a status set by hand. Nothing stored is deleted: existing connectors and ServiceNow or Halo ticket connections are
listed with `available: false` and can be deleted (the ticket connections page lists them under "Kept from a preview
install"), and turning the setting on brings everything back as it was.
docs/CAPABILITIES.md, "Preview features", has the details.

### Discovery and sign-in settings

- Credential encryption keys: secrets typed into Softwarden (connection client secrets; email, Teams and webhook secrets) are stored only as Fernet ciphertext with the id of the key that encrypted it, and never returned by the API or written to logs, audit events, exports or job arguments. See "Credential encryption keys" under "Run the full stack in Docker". Without a key, secrets can't be saved and runs say so.
- **Single sign-on.** Each organization configures its own OpenID Connect sign-in in `/api/v1/sso/settings` (Admin, capability `sso.oidc`, ETag/If-Match): a preset for Microsoft Entra ID (the tenant GUID; never `common`), Okta (the Okta domain and an optional custom authorization server ID), Google Workspace (the Workspace domains whose accounts may sign in) or any OpenID Connect provider (its `/.well-known/openid-configuration` address), with the client ID and a write-only, Fernet-encrypted client secret. Every change goes to a draft; `POST /api/v1/sso/settings/test` starts a real sign-in of your own account against the draft (in the browser; nobody is signed in and the result is recorded on that draft revision), and `POST /api/v1/sso/settings/activate` makes a draft whose test of its current revision passed the one people sign in with; `.../disable` turns SSO off. Register `{SOFTWARDEN_BASE_URL}/api/v1/auth/oidc/callback` as the redirect URI with the provider (`redirect_uri` in the settings); it never comes from the request's Host. Sign-in domains (`sign_in_domains`, unique on the installation once verified; in cloud mode a DNS TXT record must verify each one first, `SOFTWARDEN_SSO_DOMAIN_VERIFICATION`) let the sign-in page find the organization from a work email; a link `/login?org=<slug>` names it directly. The first SSO sign-in matches one active member of that organization by email and pins the identity (issuer and subject) to the account; no account is ever created, and an account that also belongs to another organization is never linked by email. A session signed in through an organization's SSO reaches only that organization (its switcher lists only it); the others need their own sign-in, and a password sign-in reaches every membership. `auth/oidc/start` and the callback have their own throttle (`SOFTWARDEN_SSO_THROTTLE_RATE`), and a failed discovery fetch is answered from the cache for 30 seconds. The provider's discovery document and keys are fetched with a 10-second timeout and cached for five minutes. In the app, Admins use **Admin › Single sign-on** (`/admin/sign-in`): a status card (Active, Disabled, or Legacy when the organization has no settings of its own; the active provider, who activated it and when, and its revision), the draft form with one set of fields per provider and the client secret shown only as "Set on DATE" with Replace, the redirect URI and the sign-in link to copy, and the sign-in domains. **Test sign-in** saves the draft first if it has changes, sends you to the provider and brings you back to `/admin/sign-in?sso_test=passed` (or `failed&reason=<code>`), which the page reports and then clears; the test panel shows the current revision's result (passed, or failed with its code and detail, by whom and when), "Not tested", or "Tested an earlier revision". **Activate draft** stays disabled, with the reason in words, until the current revision has passed; turning SSO off asks for confirmation. With `SOFTWARDEN_FORCE_LOCAL_LOGIN` set the page says so and refuses tests and activation. Break-glass: `SOFTWARDEN_FORCE_LOCAL_LOGIN=1` hides and refuses every SSO route; `manage.py sso_recovery` shows and turns SSO off from the host, and moves or frees a squatted sign-in domain ([runbook](04-development/sso-recovery-runbook.md)). Password sign-in is never removed.
- **Users and invitations.** Admins invite by email (`POST /api/v1/invitations`, or `POST /api/v1/users` as before) and get a link, `{SOFTWARDEN_BASE_URL}/invite#<token>`, shown once: copy it and send it yourself (there is no email delivery yet). The token sits in the link's fragment and travels only in request bodies (`POST /api/v1/auth/invitations/preview` and `.../accept`, public, CSRF-checked, on their own throttle, `SOFTWARDEN_INVITATION_THROTTLE_RATE`), so it never appears in a server log. Nobody is added at invite time. A new person opens the link, sets their name and a password, and is signed in with the invited role; someone who already has an account on the installation signs in as that account (password, or the inviting organization's single sign-on with an identity already linked to that account; a session signed in through another organization's single sign-on can't accept) and accepts. With more than one organization on the installation (or in cloud mode) only the link in the invitation email creates a new account: the link the Admin is shown joins an account that already exists, signed in as itself, and says nothing about whether the address has one (docs/API.md "Proof of the mailbox"). An invitation is good for 7 days and once; `POST /api/v1/invitations/{id}/resend` makes a new link (the old one stops working) and `.../revoke` ends it; a new invitation to the same email replaces the live one, and a deactivated account's invitations stop working. `GET /api/v1/users` lists each member's single sign-on identities (provider, issuer, last sign-in; never the subject) and `DELETE /api/v1/users/{id}/identities/{identity_id}` unlinks one (`DELETE /api/v1/users/{id}/identity` still unlinks all). In the app, **Users & roles** has three tabs (`?tab=` in the URL): Members (each member's identities with per-identity Unlink behind a confirmation; a shared account's say "Managed in another organization"), Invitations (status, search and filter in the URL, Resend showing the new link once, Revoke behind a confirmation) and Pending access. The invitation page keeps the link's token in the tab for an hour at most, and signing out of the app forgets it. Deactivate and reactivate are unchanged. Removing someone from an organization also unlinks their identities at providers that no organization they still belong to configures (and no legacy `SOFTWARDEN_OIDC_*` setting), so the old organization's provider keeps no foothold on the account.
- **Single sign-on auto-provision.** Off by default. With `sso_auto_provision` on in Organization settings (`PATCH /api/v1/organization`, Admin, audited), someone who signs in through the organization's active single sign-on but matches no member is not refused: they are recorded as a pending access request (`GET /api/v1/pending-access`, Admin) with no account and no role, and the sign-in page says access is pending (`/login?error=access_pending&org=<slug>`). An Admin approves with a role (`POST /api/v1/pending-access/{id}/approve`), which creates the account (no password; they sign in with single sign-on), its membership and the linked identity, or declines (`DELETE /api/v1/pending-access/{id}`). An email whose account belongs to any other organization (even if it is also a member here) can't be approved this way (409): invite them instead. A repeat sign-in that changes the request's email is audited. At most 500 requests wait per organization; beyond that sign-ins are refused with `access_pending_full`. In the app the switch is in Organization settings (disabled, with the reason, while single sign-on isn't active), and Users & roles › Pending access lists the requests with provider, email, first and last seen: Approve asks for a role, Decline confirms, and a 409 offers "Invite instead" with the email filled in.
- `SOFTWARDEN_OIDC_TENANT`, `SOFTWARDEN_OIDC_CLIENT_ID`, `SOFTWARDEN_OIDC_CLIENT_SECRET` (**legacy, deprecated**): installation-wide Entra sign-in from earlier versions. Used only while the installation has exactly one organization and that organization hasn't activated (or turned off) settings of its own; move to `/api/v1/sso/settings`. `SOFTWARDEN_BASE_URL` must be the address people browse to, because the redirect address is built from it.
- `SOFTWARDEN_IMAGE`: the image tag Compose runs, `softwarden:local` by default; pin a release tag on a server.
- **Connections.** Connectors sign in through a per-organization connection: `/api/v1/connections/microsoft` (tenant ID, application (client) ID, client secret) and `/api/v1/connections/halo` (Halo URL, client ID, secret, scope; capability `discovery.halo`; private addresses follow `SOFTWARDEN_ALLOW_PRIVATE_SERVICE_HOSTS`), Admin only, with ETag/If-Match. Secrets are write-only (`secret_set_on`, send `secret` only to replace it). `POST .../{id}/test` asks for a token and records the outcome (the response's `result` is this call's; if the connection was edited during the test it says `changed` and nothing is recorded); a Microsoft failure is classified by its AADSTS code (wrong or expired secret, unknown app or tenant, consent missing). Changing a sign-in value or the secret raises the connection's `revision`, and no connector runs on it until it is tested again (the run fails with the reason; "Run now" answers 409). A connection a connector uses can't be deleted (409 naming the connectors). The connector form's tenant, client and secret fields still work: they create or change the connector's own connection, which must then be tested. Upgrading moves each Entra connector's credentials into a connection, still encrypted; it counts as tested only when the connector's last run succeeded and nothing about it changed afterwards. The tenant ID `simulated` and the Halo URL `https://halo.simulated.invalid` never leave the machine. Like every simulated tenant and host (Okta, Google, Jira, ServiceNow, Graph email), they are allowed only with `SOFTWARDEN_DEBUG` on, in the Playwright server, or with `SOFTWARDEN_ALLOW_SIMULATED=1`; otherwise they are refused on save (a field error naming the flag), at the test (`simulation_off`) and when a run, a ticket refresh or an email starts, and a connection saved while they were allowed is kept but never runs (`doctor` warns about its connectors).
- **Okta and Google Workspace sources (capabilities `discovery.okta`, `discovery.google`; preview features, only with `SOFTWARDEN_PREVIEW_FEATURES=1`).** `okta` (connection `/api/v1/connections/okta`: the org address, an API service app's client ID and private key (PEM or JWK), scope `okta.apps.read`; the app needs the admin role Read-only Administrator) reads the org's applications as application candidates with their sign-on mode and assigned-user counts; inactive apps and Okta's own apps are skipped by default. Rate limits (`X-Rate-Limit-*`) are honored and every call goes through the address guard (a custom domain that resolves to a private or loopback address is refused). `google_workspace` (connection `/api/v1/connections/google_workspace`: a service account key file and the administrator it acts as through **domain-wide delegation, a tenant-wide grant a super administrator makes**, scope `admin.reports.audit.readonly` only) reads the OAuth token audit log of the last 30 days (scope `days`, up to 180) and keeps, per third-party app, how many people authorized it, with which scopes and the high-risk ones: never who. Okta refuses a run whose listing comes back empty while it has live candidates; a Google window with no authorization at all is a note on the run and changes nothing. Simulated: Okta `https://okta.simulated.invalid`, Google an administrator in `google.simulated.invalid`. docs/PERMISSIONS.md lists every scope and grant.
- **Entra sources.** The `entra` source lists enterprise applications and app registrations, merged by application (client) ID, with owners and the end dates of their client secrets and certificates (`DiscoveredCredential`, never key material); Microsoft first-party apps (scope `first_party_tenants`) are skipped and counted; Copilot Studio agents (by their tags) and, with scope `include_agent_identities`, Entra Agent ID agent identities become AI agent candidates. The `entra_licenses` source (`"source": "entra_licenses"`) reads `subscribedSkus` into license observations for the seat review. `POST /api/v1/connectors/{id}/access-check` (Admin) makes one one-item read per permission and names any that is missing; optional ones (`User.ReadBasic.All` for owners' names, `AgentIdentity.Read.All`) are reported, not failed; the result is the connector's `access_check`, and `permissions` lists what each source uses. `GET /api/v1/discovery/credentials` (any role) lists discovered credentials; live ones feed the credential expiry reminders and the dashboard's expiring credentials. Graph throttling (429/503) is retried after `Retry-After`, else with exponential backoff, within 15 minutes of waiting per run. Permissions: docs/PERMISSIONS.md.
- **Azure, Power Platform and Halo sources (capabilities `discovery.azure`, `discovery.powerplatform`, `discovery.halo`, in every edition).** `azure` (Microsoft connection; Azure role Reader on the subscriptions or a management group) reads Logic Apps, Function Apps, optionally App Services (scope `include_app_services`) and Automation runbooks from Azure Resource Manager, per subscription (scope `subscriptions`, empty for every subscription the app can see), as component candidates. `powerplatform` (Microsoft connection; an application user in each environment) reads Copilot Studio agents from each environment's Dataverse (scope `environment_urls`) as AI agent candidates, cloud flows with `include_cloud_flows`, and every environment through the admin-equivalent Power Platform admin API only with `all_environments`. `halo` (Halo connection, `"halo_connection": "<id>"`) reads Halo assets as application candidates with their Halo asset ID. One Microsoft connection gets a token per resource (Graph, Azure Resource Manager, each Dataverse environment, the admin API), and a token is sent only to that resource's host. A subscription or environment that can't be read is noted on the run and its candidates keep their state (`counts.not_read`). Each has an access check naming what is missing (the Azure action and scope and the fix, the Dataverse privilege, the Halo scope). A community organization is refused with 403 naming the capability. Simulated tenants: Microsoft connection tenant `simulated`, Halo `https://halo.simulated.invalid`.
- **Reconciliation.** Discovery never overwrites curated data. The queue (`GET /discovery/candidates`, statuses `candidates`, `new`, `changed`, `linked`, `dismissed`, `gone`, and the linked filters `missing` and `differs`, each counted) offers each candidate up to three records of compatible kinds with a similar name and a score (`GET /discovery/observations/<id>/suggestions?limit=` for up to 10); link, create (every source kind maps to its record kind with the source's IDs prefilled) and dismiss with a reason are audited, and `reopen` undoes the decision and keeps every record; `reopen {"archive": true}` also archives the record a create made, refused (409) if it was changed since or anything references it. An object the source still has but the scope leaves out (a filter, a type or subscription no longer read) is `out_of_scope`: it keeps its state and is never "no longer seen". For linked records, **source differs** (`GET /discovery/observations/<id>/drift`) lists each field the source speaks for (Entra: name, description, documentation URL, Entra IDs; Azure: name, description, resource ID, environment tag; Power Platform: name, environment ID, external ID, a flow's description; Halo: name) with the record's value, the source's and since when; `drift/apply` is an ordinary audited record edit under the record's `If-Match` (the record's ETag, also `record_etag`) with the reviewed source values in a required `seen`, and `drift/ignore` (also with `seen`) keeps the record's value until the source says something new. Differences are recomputed after every run, decision and record edit and never applied on their own. **No longer seen in source**: a linked record whose object a run no longer lists is a Needs attention row ("No longer seen in source", `discovery_missing`; counted in the badge and a digest section) until someone keeps it (`missing/acknowledge`) or archives it (`missing/archive`, under the record's `If-Match`; refused while another source still sees it); it clears itself when the object comes back, and a scope a run couldn't read never makes anything missing. **License seats**: every Entra licenses run syncs only pools bound to the SKU (their SKU ID) with `seat_sync` on (held, with a run note, when two connectors report the same SKU); other bound pools get proposals; pools without a SKU ID never change. Unbound SKUs (`unbound` in `GET /license-pools/seat-review`) become a pool (`POST /license-pools/unbound/<observation>/create`) or bind an existing pool without a SKU ID (`GET /license-pools?sku_id=none`; `POST /license-pools/<id>/bind`, `If-Match` on the pool). A syncing pool says which licenses connector it syncs from (`synced_from`) or that its sync is held (`sync_held`, two sources report the SKU). Viewers read all of it; Editors and Admins act.
- **Runs, scheduling and history.** Every connector run is its own background job (`discovery.run`, whose only argument is the connector's ID). **Run now** (`POST /api/v1/connectors/{id}/run`, Admin) queues a run and answers 202 with the connector, whose `active_run` is the queued run, and a `Location` header for it (`/api/v1/connectors/{id}/runs/{run id}`, poll it for progress); 409 while the connector already has a queued or running run. The `discovery.connectors` schedule, every minute, only queues: each daily connector once a day after 02:00 organization time. It never runs a connector itself. The worker runs these jobs in a lane of threads beside its tick (2 at once per worker; `run_worker --long-jobs N` or `SOFTWARDEN_WORKER_LONG_JOBS`, 1 or more: 0 is refused at start-up), taking an organization with nothing running first, so a slow tenant holds up no schedule, no email and no other organization. `run_worker --once` runs them inline. A run holds a lease (50 minutes: the 40-minute run limit plus a margin), renewed as it reads. If its worker stops or stalls, the lease runs out, the run is marked failed with the reason, and the next run can start; a late finisher's result is discarded and never overwrites the newer run. A worker that is stopped fails its running runs at their next request ("run it again") rather than leaving the connector locked; turning a connector off fails its queued run before it reads anything. **History:** `GET /api/v1/discovery/runs` (every member; newest first, paged with `cursor`; filters `connector`, `status` (queued, running, succeeded, failed), `trigger` (manual, scheduled), `from`/`to` as YYYY-MM-DD in the organization's timezone). Each run has when it was queued, started and finished, `duration_seconds`, trigger, who started it, status, `error` in Softwarden's words, `counts`, `skipped` (each filter's label and count) and `notes`. `GET /api/v1/connectors/{id}/runs` still returns that connector's last 50 as an array. `GET /api/v1/discovery/runs/{id}` (every member) is one run by its own ID, the run page's address (`/discovery/runs/{id}`; the older `/discovery/runs/{connector}/{run}` redirects to it). `GET /api/v1/discovery/sources` (every member) says what each source needs before any connector of it exists: label, capability and whether this organization's edition has it, connection kind, `permissions` (as on a connector), `scope_defaults` and filter labels; the guided setup's Prepare step lists the permissions from it. A connector's `connection` carries the connection's `last_test` (null when never tested), so the SPA tells "not tested" from "changed since last test".
- **The assistant (capability `assistant`, off by default).** Claude suggests link, create or dismiss for undecided discovery candidates, each with a confidence from 0 to 1 and a short reason; Editors decide (`POST /api/v1/discovery/observations/{id}/assistant/accept` performs the suggested action as an ordinary audited decision, `.../assistant/reject` records a no, and any link, create or dismiss records on the suggestion whether it was accepted, overridden or ignored); nothing is ever applied on its own. Configure it as an Admin in `/api/v1/assistant/settings` (ETag/If-Match): an Anthropic API key (write-only, Fernet-encrypted), a monthly cost cap in USD (default 10.00) and `enabled`. Without its own key an organization can use the installation's `ANTHROPIC_API_KEY` only when `SOFTWARDEN_ASSISTANT_INSTALLATION_CAP_USD` is set (USD per organization per month); it is then held to the lower of its cap and that ceiling. Unset, the installation key is never used. The model is installation-wide: `SOFTWARDEN_ASSISTANT_MODEL` (default `claude-sonnet-5-5`); `SOFTWARDEN_ASSISTANT_PRICES` (JSON, USD per million tokens) prices another model, and a model with no price is refused. A run that sees new or changed objects queues a batch (a `discovery.assistant` job, ID only); an Editor can ask for one with `POST /api/v1/assistant/batches`. A candidate is sent again only after its fingerprint changes. Before each call the worst case is reserved against the cap; a batch that would pass it stops with `cap_reached`. A batch that leaves candidates over its limit of 50 queues a follow-up while the cap allows. `GET /api/v1/assistant/usage?month=YYYY-MM` (Admin) is the usage log (four token counts and cost per call) and the month's total. In the SPA: Admin › Assistant (the settings, the key in use, this month against the cap, the model's price) and its Usage log (`?month=YYYY-MM`); the Discovery queue shows each candidate's suggestion with Accept and Reject for Editors and "Ask the assistant". What is sent to Anthropic, and what never is: docs/PERMISSIONS.md; configuration: docs/CAPABILITIES.md.
- The Entra client reads only, from the fixed hosts `login.microsoftonline.com` and `graph.microsoft.com`. The tenant ID `simulated` selects the synthetic tenant. Connecting a real tenant needs an app registration and admin consent ([FIRST_RUN.md](FIRST_RUN.md), [PERMISSIONS.md](PERMISSIONS.md)).

### Vendor risk file

Each vendor has a risk file (community, capability `vendor_risk`): the security questionnaire's status and dates, the
assurance report (SOC 2 Type I or II, ISO 27001 or another; its expiry is the issue date plus a validity, 12 months by
default), the DPA, the subprocessor list, an overall risk tier and notes, linking the vendor's own attachments. Dated
documents (SOC 2 reports, ISO 27001 certificates, penetration tests, questionnaires, DPAs, insurance certificates)
read as current, expiring (within the organization's largest reminder threshold) or expired, and each expiry date is
a reminder: the built-in "Vendor risk documents" rule notifies 60, 30 and 7 days before, and the reminders show in
Needs attention. A high or critical vendor with no current SOC 2 or equivalent, and a vendor that processes personal
data without a signed DPA, are gaps: a Needs attention "Vendor risk" queue (for the coordinator) and two data-quality
checks on the vendor's applications. API: `GET/PATCH /api/v1/vendors/{id}/risk`, `/vendors/{id}/risk-documents`,
`/vendor-risk-documents` (filters `tier`, `status`, `expiring_within`; `export.csv`) and
`GET /vendors/risk-overview` (filters `tier`, `gap`, `expiring_within`, `expired`; `export.csv`); a vendor's detail
carries a `risk` summary. `seed_demo` gives Workday, Zoom and Zylker risk files (Zoom has both gaps). The vendor page and
the Vendor risk page show them.

### Data-flow map

Integrations are data flows (capability `data_flows`, every edition). Besides its classification, an integration
records which kinds of data it carries: `data_categories` (personal, special-category personal, financial,
credentials or secrets, health, customer content, other), with `contains_personal_data` derived. "Where does
confidential data go?" is `GET /api/v1/reports/data-flows` (filters `min_classification`, `category`, `source`,
`target`, `record`, `risk`; `/graph` for the map, `/export.csv`): every live flow with both ends, their own
classifications and each end's vendor (with its DPA and assurance from the vendor risk file), and its risks:
confidential or personal data to a vendor with no DPA, no authentication to an external vendor, or a flow classified above the
record receiving it. Risky flows are a Needs attention "Data flows" queue, and two data-quality checks ask for an
integration's classification and, from confidential up, its categories. The screens come with the SPA
package. See docs/API.md "The data-flow map".

### Cloud signup and the organization lifecycle

**Cloud mode is not supported for production in 1.0.** Organizations on one installation can't yet be kept from
taking each other's email addresses or using its mail, and platform staff have no second factor
([docs/CLOUD.md](CLOUD.md#not-supported-for-production-in-10)). Evaluate it with test data; run 1.0 self-hosted, one installation per organization (the same gaps apply to
several organizations sharing a self-hosted installation).

Public signup is off by default. For the hosted service set `SOFTWARDEN_SIGNUP_ENABLED=1` and email
(`SOFTWARDEN_SMTP_HOST`, or Mailpit locally): `/signup` then emails a confirmation link, and confirming it (with the
password again) creates the account, a new `cloud` organization and its Admin. Invitations are emailed too, through
the organization's own email settings or the installation's; the copy-once link still works without either. An Admin can export all data
(`POST /api/v1/organization/exports`, a zip for 7 days) and, in a cloud organization, delete the organization after a
grace period (`SOFTWARDEN_ORG_DELETION_GRACE_DAYS`, 30 days; cancelable until then). Accounts left with no
organization are deactivated; if their address signs up or is invited again, the old account is retired
(`retired+<id>@invalid`, kept for other organizations' history) and a fresh one is made. See docs/API.md "Signup and the
organization lifecycle" and docs/ENV.md.

**Limits and tenant backups.** A cloud organization has generous default limits (5,000 records, 10
connectors, 50 active members, 5 GB of attachments, 1,200 API reads and 300 writes a minute for the organization as a
whole); community is unlimited by default, and platform staff can set one organization's value. A
create past a limit answers `409 /problems/limit-reached`; updates and deletes never do, and lowering a limit removes
nothing. Members see their limits and usage at `GET /api/v1/organization/limits`. Cloud organizations
(capability `org.tenant_backups`) get a nightly backup of their data, listed and downloaded with the exports; the
newest `SOFTWARDEN_TENANT_BACKUP_RETENTION` (7) are kept. An operator can also make an export a customer asked for
through support (`POST /api/v1/platform/organizations/{id}/exports`); only the organization's Admins can download it.
Transactional email through a provider is not built yet (no provider account). See docs/API.md "Limits" and
docs/CAPABILITIES.md.

### End-of-life tracking

Applications and components that run on your own servers can be mapped to an [endoflife.date](https://endoflife.date)
product (capability `eol`, every edition): `PATCH /api/v1/applications/{id}/end-of-life {"product": "postgresql"}`
derives the release cycle from the application's version (16.4 is cycle 16), or takes `version` or `cycle`
explicitly; an application's instances can each have their own version. Each tracked version shows its status
(supported, security fixes only, end of life, unknown), its end-of-life date and the days left, in the record's
`end_of_life`, the overview `GET /api/v1/end-of-life` (filters and a CSV) and a Needs attention queue (end of life,
or within 180 days). An end-of-life date is also a reminder: the built-in "End of life" notification rule emails the
record's IT steward (else its technical owner) 90, 30 and 7 days before, then every 30 days while the version is past its end of life (or flagged end of life with no date, counted from the day it was tracked) until the reminder is acknowledged (`repeat_every_days` on any rule; an organization whose End of life rule already had escalation steps of its own keeps `escalate_when_acknowledged` on, so its repeats continue after an acknowledgment); a flag-only version is worded "End of life (no date published), tracked since DATE"; when endoflife.date later publishes a date for that cycle, the reminder (acknowledged or not) is replaced by a dated one, which notifies afresh, and a date already 30 or more days past gives one catch-up notice, then the 30-day marks from that date. It is not repeated in the daily digest. The worker's `eol.refresh` job reads endoflife.date once a day (04:45 UTC) for the products
someone tracks, sending back ETags so unchanged data costs a 304; nothing in a request touches the network.
Air-gapped: set `SOFTWARDEN_EOL_ENABLED=0` and load a saved `https://endoflife.date/api/v1/products/full` with
`manage.py eol_import FILE`; `manage.py eol_refresh` refreshes now. See docs/04-development/operations.md.

### Offboarding and access review

"Priya is leaving: what does she own?" `GET /api/v1/people/{id}/footprint` (any role) lists everywhere a person
appears: records, AI agents (owned, or running as her email or Entra object ID) and integrations she owns, IT
stewardship, teams, vendors, contracts, renewals, reviews she confirmed, change assessments, data-quality exceptions,
discovery sources she reviews, discovered apps whose Entra owners match her, and (Admins) notification rules and her
account: role, IT coordinator, API tokens, calendar feed, saved views and subscriptions. Licenses aren't read: that
needs User.Read.All, which Softwarden doesn't request. `footprint.csv` exports it. `POST /api/v1/people/{id}/reassign
{"to": "<person id>", "roles": ["business_owner", "technical_owner", ...], "dry_run": true}` (Editors and Admins)
hands the chosen roles to an active colleague in one transaction, one audited change per row marked `via:
offboarding`; it never deletes anything. `GET /api/v1/reports/access-review` lists every live record's owners and
flags inactive owners, owners whose account was deactivated or removed, records with no owner, and Entra owners that
differ from the catalog's (filters `kind`, `flag`, `owner`, `include_retired`; `export.csv`). Every part reads stored
data only; nothing calls Microsoft. See docs/API.md "Offboarding and access review".

### Ticket links

Change assessments and renewals can link the Jira, ServiceNow, Halo or other ticket that tracks the work (capability
`ticket_links`, every edition): an Editor pastes the ticket's address (`POST /api/v1/assessments/{id}/ticket-links
{"url": "https://contoso.atlassian.net/browse/ITOPS-123"}`, or under `/renewals/{id}/`) and the system and key are
parsed from it; the status (open, in progress, resolved, closed, unknown) can be set by hand. With a ticket
connection (Administration, `/api/v1/ticket-connections`, Admin: a Jira site with an account email and API token, a
ServiceNow instance with a user and password, or the Halo connection), the worker's `tickets.refresh` job
reads open tickets' status hourly by key from the connection's own address, through the same outbound rules as
webhooks and Halo (never the link's URL). An Admin can also allow creating a ticket from an assessment or renewal
(`create_enabled`, off by default; every attempt is audited). The secrets are encrypted and write-only. The hosts
`jira.simulated.invalid`, `servicenow.simulated.invalid` and `halo.simulated.invalid` select synthetic systems.
ServiceNow and Halo ticket connections are preview features (capability `preview`, only with
`SOFTWARDEN_PREVIEW_FEATURES=1`): without it only Jira is offered and read, and ServiceNow and Halo links are kept
with a status set by hand. See docs/API.md "Ticket links" and docs/PERMISSIONS.md "Ticket connections".

### Email and the mail catcher

Each organization chooses how it sends email in Administration › Email settings (`/api/v1/notification-settings/email`, Admin): **Microsoft Graph** (`sendMail` as the app from one mailbox; grant `Mail.Send` only through Exchange RBAC for Applications scoped to that mailbox, never as an Entra API permission: [docs/PERMISSIONS.md](PERMISSIONS.md), "Email via Microsoft Graph"), an **SMTP server**, or the **installation default**. The installation default is the server's environment, and is what an organization without settings uses (including the daily digest, which is a delivery like any other): `SOFTWARDEN_SMTP_HOST`, `SOFTWARDEN_SMTP_PORT` (587), `SOFTWARDEN_SMTP_USER`, `SOFTWARDEN_SMTP_PASSWORD` (never logged or returned), `SOFTWARDEN_SMTP_TLS` (1), `SOFTWARDEN_EMAIL_FROM` and `SOFTWARDEN_BASE_URL` (the address links start with). With no host set (and no organization settings), email is off: digests and other email deliveries are recorded as skipped, and every action stays in Needs attention. SMTP AUTH with a password against Exchange Online is off by default for existing tenants from the end of December 2026; use Graph for Microsoft 365. The Graph client secret and the SMTP password are encrypted (write-only). **Test connection** checks the settings without sending (for Graph it only gets a token, which doesn't prove the mailbox scope); **Send test email** sends a real message to your own address and records it in the notification log. The tenant ID `simulated` selects a synthetic Graph (`core/graph_simulator.py`; sender mailboxes starting `denied@` or `missing@` show the refusals).

Teams notifications go to a channel's **Workflows** webhook ("Send webhook alerts to a channel"; Office 365 connectors were retired in May 2026 and are refused) as Adaptive Cards: Administration › Teams destinations (`/api/v1/notification-settings/teams-destinations`). Generic webhooks (`/api/v1/notification-settings/webhook-destinations`, and `/api/v1/webhooks`, the same rows) are signed with HMAC SHA-256 (`X-Softwarden-Signature: t=<unix>,v1=<hex>` over `"<t>." + body`). Both addresses are bearer secrets (encrypted, write-only; only the host is shown), must be https and may not point at private, loopback or link-local networks (checked again after DNS resolution at send time). An organization's SMTP host (and a Halo URL) may be a private relay but not loopback, link-local or cloud metadata addresses (169.254.169.254, `fd00:ec2::254`, `100.100.100.200`); set `SOFTWARDEN_ALLOW_PRIVATE_SERVICE_HOSTS=false` on a hosted, multi-organization install to refuse private networks (RFC 1918, ULA, carrier-grade NAT) as well (default `true`; the server's own `SOFTWARDEN_SMTP_HOST` isn't restricted); every send has a wall-clock deadline (30 s for webhooks, 60 s for SMTP). Each has **Send test**.

**Webhooks** (Admin only, `/api/v1/webhooks`; docs/API.md "Webhooks") post signed events to your own HTTPS endpoint: `record.*` (created, updated with each field's before and after, archived, restored, deleted), `relationship.*`, `renewal.*`, `discovery.candidate` and `reminder.*`; subscribe to a type or a whole family (`record.*`). Events are written to an outbox in the change's own transaction (`WebhookEvent`: a change that rolls back sends nothing, a saved change always sends) and posted by the worker on its next tick (one a minute; the `webhooks.outbox` schedule), never inside your request. A failed post is retried after 1 min, 5 min, 30 min, 2 h and 6 h (±10 %; `SOFTWARDEN_WEBHOOK_MAX_ATTEMPTS`, default 6 attempts); a 410 Gone, or `SOFTWARDEN_WEBHOOK_DISABLE_AFTER` (default 5) deliveries in a row that failed after their retries, turns the endpoint off, audited and shown to Admins (`auth/me` `webhook_problem`). Only event deliveries count towards that; a ping or a rule's notice fails only itself. Finished notification deliveries of every channel are deleted daily after 30 days when sent and 90 when failed or skipped (`SOFTWARDEN_DELIVERY_RETENTION_SENT_DAYS`, `SOFTWARDEN_DELIVERY_RETENTION_FAILED_DAYS`; a live reminder's notices and digests' deliveries are kept). Every attempt is in the delivery log (`/api/v1/webhook-deliveries`: status code, duration, a scrubbed answer excerpt, the next attempt; resend), **Ping** sends a signed test now, and **Rotate secret** keeps the old secret signing beside the new one for a grace period (default 24 h). In the app: Administration › Webhooks (add, edit, events by family, Ping with its answer, Rotate secret, Delete) and Administration › Webhook log (`/admin/webhooks/deliveries`, filters in the URL; each delivery's attempts and payload; Resend).

Every message is a delivery (`/api/v1/notification-log`, Admin): queued with a dedupe key, sent by the worker as a job, retried on 429 and 503 after `Retry-After` (else 1, 4 and 16 minutes), never retried after an ambiguous failure (a timeout after the request was sent: it may have arrived), and resendable (`POST /api/v1/notification-log/{id}/resend`). The log filters by `channel`, `status`, `kind`, `reminder`, `rule`, `from` and `to`. The daily digest is one delivery per user and day (kind `digest`, key `digest:{user id}:{date}`): it uses the organization's email settings, appears in the log, and `/api/v1/admin/digests` (the digest log, with Retry now) reads its status, attempts and error from the delivery.

**Notification rules** (Administration, `/api/v1/notification-rules`, Admin only for reads and writes: a rule names who is emailed and where) decide when reminders are announced and to whom. A rule covers reminder types (`source_types`), sends at each lead time before the due date (`lead_times_days`, 0 = on the day) and at each escalation step after it (`escalation_days`, plus every multiple of `repeat_every_days` when set), by email (`send_email`) and to Teams and webhook destinations; its audience is the reminder's routed owner (`notify_routed`), people, a team's members and every member with a role, and escalations also reach the escalation people, team and roles. When routing finds nobody, the rule's fallback person and team are emailed, else the IT coordinator. Filters: criticality, record kind, vendor and minimum annual value. Notices go once the organization's local time has reached its digest time (at the latest 23:00, so the hourly run reaches it in every time zone). Each lead and step is sent once per notification cycle (per reminder, cycle, rule, lead, channel and recipient): a date that moves a little either way repeats nothing, while a date moved later by at least a lead (an extended contract) gets that lead again; a lead missed while the worker was down, or a reminder first seen inside a lead, sends the nearest lead once, not the ones before it; a rule that is created, turned on or widened (a Teams channel, a person, a lead time or a looser filter added; and the built-ins, on their first run after an upgrade) records what it adds for stages that began before today as done (`baseline` rows in the log, filter `?baseline=`) instead of sending them, so nothing bursts out; a snoozed reminder is quiet through its date; an acknowledged one gets no advance notices but still escalates (unless `escalate_when_acknowledged` is off); a moved date gets its own notices. A member can turn off reminder emails in their profile (`PATCH /api/v1/auth/me/preferences {"reminders_enabled": false}`). The `notify.rules` schedule runs hourly at :25, after `reminders.generate`. Every organization starts with built-in rules, editable but never deleted: Renewals and contracts (90, 60, 30, 7 days before), Record reviews (on the due date), Periodic reviews (30 days before and on the date), Custom dates (30 and 7), Credential expiry (30, 7, 1), Vendor risk documents (60, 30, 7), End of life (90, 30, 7, then every 30 days until acknowledged), each emailing the routed owner, and the Daily digest (`enabled` and `digest_time`, the organization's digest time). `GET /notification-rules/{id}/preview?days=60` shows what a rule would send (no writes); `POST /notification-rules/{id}/test-send` `{"email": true, "teams_destination": "<id>"}` sends a sample now (kind `test`). Teams, vendors and destinations a rule names can't be deleted until the rule stops naming them.

**Saved views and subscriptions.** Saved filters are saved views: `/api/v1/saved-filters` (every member) keeps a name, the list's query (only the filters the list page applies, plus `q`, `tag` and custom-field filters) and optionally its `columns` (the list's column ids in order, `cf_<name>` for custom fields; empty for the list's defaults). A view is private to its owner unless `shared` (Editors and Admins share); `PATCH /saved-filters/{id}` changes name, query, columns or sharing (If-Match): your own private view, or a shared one you own while an Editor or Admin, or any shared view as an Admin. `/api/v1/saved-view-subscriptions` emails a view's rows weekly: `POST {"saved_view": "<id>", "weekday": 2}` subscribes you (0 Monday to 6 Sunday); an Admin can add `"user": <id>` for another member who can see the view. You see and manage your own (Admins everyone's): `PATCH {"weekday", "active"}`, `DELETE`, and `POST /saved-view-subscriptions/{id}/test-send` to get this week's email now (once a minute). A private view's email is never shown to anyone else in the notification log. The `saved_views.subscriptions` schedule (hourly at :26) sends on the weekday of the organization's local date once it reaches the notification send time (digest time, at the latest 23:00): the rows exactly as your own list shows them (your role, the same filters and order), the view's columns, up to 50 rows and "and N more", and a link (from `SOFTWARDEN_BASE_URL`) that opens the list with the view's filter. Once per subscription and date (a rerun sends nothing). Nothing is sent, and the notification log records why as skipped, when the view was deleted, you can no longer see it or open its list, its filter has problems, your account is deactivated, or you turned saved view emails off (`PATCH /api/v1/auth/me/preferences {"subscriptions_enabled": false}`).

For local development, Mailpit catches every message on your machine (web view on http://127.0.0.1:8025, SMTP on 127.0.0.1:1025). The dev stack (`compose.dev.yaml`) starts it and uses it as the installation default; with the API and worker outside Docker:

cd apps/api

Run `runserver` with the same variables for **Send test email** to reach Mailpit (or choose SMTP in Email settings with host `127.0.0.1`, port 1025, security none). Never point it at a real mail server with real addresses: the demo users are `@example.test`, and this build is for synthetic data only.

## Capabilities

Every gated feature checks a capability name, never the edition (docs/CAPABILITIES.md lists them). Editions map to sets
of names in `apps/api/core/capabilities.py`, and `tests/test_capabilities.py` fails if code outside
`core/capabilities.py`, `core/limits.py` (the per-edition limit defaults) and `core/models.py` compares an edition.

- **In code:** call `require_capability(org, name)` after the role check, so a Viewer refused for their role still
  gets the role message, or `has_capability(org, name)` to branch. An unknown name raises `ValueError`, so a typo fails
  in tests instead of refusing quietly. A route declares its capability with `policy(..., capability=name)` or
  `required_capability`.
- **The route ledger:** `ROLE_LEDGER` in `tests/test_permissions.py` gives every organization route, every method, its
  minimum role and its capability (`-` for none), so a new route fails until it has a line.
  `tests/test_capabilities.py` fails a route that declares a capability its line lacks, and calls every route whose
  line names one as the Admin of an organization without it (a platform revoke, since every edition has every feature
  in this repository): it must answer `403 /problems/capability-required` naming it.
- **The coverage rule:** every name community lacks needs an entry in `COVERAGE` in `tests/test_capabilities.py`, the
  call that proves its gate. A gated name without a real endpoint is tested through a test-only route
  (`tests/capability_urls.py`, never in the shipped URLconf); when the feature ships, its entry moves to the real
  endpoint. Adding a name to the cloud or enterprise set without a `COVERAGE` entry fails the suite.
- **Turning a feature off in tests:** `tests.conftest.revoke_capability(org, name)` revokes it as platform staff
  would; the Playwright server has `POST /api/v1/e2e/capability-override` for the same.
- **Releasing a preview feature:** one place reads `SOFTWARDEN_PREVIEW_FEATURES`, `capabilities(org)`. Take the
  name out of `PREVIEW_ONLY` in `core/capabilities.py`; for a ticket system, set its entry in
  `tickets/services.SYSTEM_CAPABILITY` to `None`; for a discovery source whose capability is already released (as
  license usage is), take it out of `PREVIEW_SOURCES`.
- **SAML and SCIM** come from an optional `ee` package that isn't part of this repository. `softwarden/ee.py` says
  whether it is installed; without it, `capabilities(org)` drops `sso.saml` and `scim` for every organization, their
  routes aren't served, and the code that would use the package refuses with the capability problem first
  (`tests/test_ee_absent.py`). The package brings its own tests and screens.

## Data rules

- Every tenant table has a UUID `id`, an `organization_id`, a `UNIQUE (organization_id, id)` key and composite foreign
  keys (`organization_id` plus the reference), so a row can only point at a row of its own organization. Another
  organization's row reads as a 404, the same as one that doesn't exist. The cross-tenant suite
  (`apps/api/tests/test_tenancy.py`) covers every model.
- Every write goes through a service function that validates, scopes to the organization and writes an `AuditEvent` in
  the same transaction. Views and serializers never save domain models.
- Every model change ships with a migration. Migrations are forward-only, and an applied one is never edited
  (`apps/api/tests/migration_hashes.json` holds their hashes).
- The SAML and SCIM models (`SsoSettings`' `saml_*` fields, `SamlAssertion`, `ScimToken`, `ScimUser`, `ScimGroup`, `ScimGroupMember`) and
  their tables stay, because migrations are forward-only; they are unused unless the optional `ee` package is installed.

## UI rules

- Design tokens only: colors, type and motion come from `apps/web/src/design/tokens.json` (`npm run tokens` writes
  `tokens.css`), and `npm run lint` refuses a color written anywhere else. Reuse shadcn/ui and `src/components` first.
- Status is shown as a glyph plus text (`✓ Confirmed`, `! Overdue`); color is a second channel, never the only one. A gap
  is a dashed chip that names what is missing ("No business owner"), never just "Missing".
- Every screen has its loading, empty, error and viewer states: skeletons shaped like the result, an empty state that
  says what belongs there and one next step, an error that says what failed and whether anything was saved, and for a
  role that can't act, which role can.
- Filters, sort, search, tabs and pages live in the URL, so a view can be shared and survives a reload.
- WCAG 2.2 AA in the light and dark themes: landmarks and one `h1` per page, visible focus, keyboard access to every
  action, a table beside every graph, results announced; the Playwright suite runs axe on the pages it visits.
- American spelling in the UI, API messages and docs; `npm run lint` checks it.

### CI and releases

`.github/workflows/ci.yml` runs on every push to `main` and every pull request, except those that change only `site/` (the website; `.github/workflows/site.yml` builds it), and the `audit` job alone every Monday. Every job has a `timeout-minutes`. A green run means no test failed, none was flaky and pytest skipped only the live-tenant tests:

- `api`, `mcp`, `web`: the gates above (Ruff, mypy, `makemigrations --check`, pytest, ESLint, tsc, the Vite build and its size budget) and the generated API types check. The api job runs pytest with `-m "not otel"` and `--junitxml`, then `ops/ci/test-report-check.py pytest-skips --allow "live test:"` fails the job if any test skipped for another reason (a missing tool on the runner, say), so its summary shows only the five live-tenant skips. It installs `postgresql-client-17` from the PostgreSQL apt repository (signed by the key committed in `docker/pgdg/`), so `tests/test_backup.py`'s full backup runs with the real `pg_dump` and `pg_restore` (that test fails rather than skips when `CI` is set);
- `image`: two legs. The default image and the MCP image build; and the image with `WITH_OTEL=1` builds, the tests marked `otel` run with the extra installed (`uv sync --extra otel`; none may skip), and `ops/ci/otel-image-probe.sh` runs the same probe (`apps/api/tests/otel_probe.py`) inside that image as its web and worker processes;
- `e2e`: the whole Playwright suite in four shards (`npx playwright test --shard i/4`), one runner each. CI retries a failed test once, and `ops/ci/test-report-check.py playwright` then fails the shard on any test the JSON report (`apps/web/test-results/results.json`) lists as flaky, naming it with its first error: the retry tells a flake from a steady failure, it never turns a run green;
- `audit`: `pip-audit` on the API's and the MCP server's locked runtime requirements (`uv export --frozen --no-dev`), and `npm audit --omit=dev` in `apps/web` at moderate and above through `ops/ci/npm-audit-check.py`, which accepts only the advisories `apps/web/audit-allowlist.json` lists, each with the reason it doesn't apply and a `review_by` date after which it fails again;
- `deploy-config`: `helm lint` and `helm template` (default values and `examples/external-postgres.yaml`), `caddy validate` of `docker/Caddyfile` under the caddy image `compose.yaml` pins, `shellcheck` on `ops/` and `scripts/`, and `ops/ci/check-pins.sh`, which fails if a workflow `uses:` an action by anything but a full commit SHA (with its version in a comment), if a Dockerfile `FROM`/`COPY --from`, a Compose image or a CI service image has no `@sha256:` digest, if a `uvx` tool has no version, or if an apt source names no `signed-by=` key or a signing key is fetched at run time instead of committed. `.github/dependabot.yml` proposes the updates weekly (actions, Docker and Compose images, uv and npm);
- `compose-first-run`: `docker compose up -d --build --wait` with no `.env`, `bootstrap_admin --prepare`, `doctor --json` with no failure, then `/` and `/readyz` through Caddy, the slow-body smoke test, and `ops/ci/inapp-backup-rehearsal.sh`: demo data and an attachment, `backup_now --inline` in the worker, the set and the generated key copied out, and `ops/restore.sh --rehearse` on it, which must check an attachment file and the manifest;
- `migrate-from-previous`: `ops/ci/restore-previous.sh`, the upgrade rehearsal. It builds the previous release tag (the newest `v*` tag before this commit; until the first release is tagged, the job skips) from a `git worktree`, seeds it (demo data, an attachment, a credential, and a second organization with its own Admin, a notification rule named like a built-in this release adds, a webhook endpoint and a queued job), backs it up with that release's `ops/backup.sh`, then restores the set under this commit's image in a second Compose project: `restore.sh --rehearse --migrate`, a real `restore.sh --yes` (which runs the migrate service before the app starts), `migrate --check`, `upgrade_check --manifest`, the seeded data (the built-in renamed around the organization's rule, the webhook's secrets, the job still queued), every record, contract and membership still in its organization, and `doctor`. Both projects and their volumes are removed by project name afterwards. Run it locally the same way, from Git Bash on Windows too: `bash ops/ci/restore-previous.sh` (about 5 minutes after the first image builds; a previous release that still publishes its database does so on 127.0.0.1:55434, `RESTORE_PREV_DB_PORT` changes it; this commit's stack publishes none).

`.github/workflows/release.yml` runs on a pushed `v*` tag: it publishes `ghcr.io/softwarden/softwarden` and `ghcr.io/softwarden/softwarden-mcp` (the repository [Softwarden/softwarden](https://github.com/Softwarden/softwarden) publishes to `ghcr.io/softwarden`) tagged `X.Y.Z`, `X.Y` and `latest`, with an SBOM and provenance, and creates the GitHub Release from that version's section of `CHANGELOG.md` (`ops/ci/changelog-section.sh`) with both image digests. Before it pushes anything, `ops/ci/release-preflight.sh` checks the tag is a strict `vX.Y.Z[-pre]`, the tagged commit is on `main`, `apps/api/pyproject.toml` and `Chart.yaml` carry the same version, the CHANGELOG heading has a real date, and the version isn't already in the registry; then the whole of `ci.yml` runs on that commit and the `release` environment waits for approval. The images are pushed by digest, attested and started as a Compose stack; only then are the tags added (`latest` only for the highest stable version, `X.Y` only for the highest of its line). The steps are in [Cutting a release](#cutting-a-release).

Postgres must be running for both suites. Playwright never touches your development database or servers: it drops and recreates its own `softwarden_e2e` database on every run (`apps/api/e2e_db.py`, which refuses any name that doesn't end in `_e2e`), migrates and seeds it, then starts its own API on port 8011 (`apps/api/e2e_server.py`: `runserver --noreload` with a larger listen backlog, because parallel workers overflowed the default one and Windows answered with connection refused) and Vite on port 5174, and fails rather than reuse a server that is already running there. The e2e API servers keep their database connections (`SOFTWARDEN_DB_CONN_MAX_AGE=60`, with health checks; unset, the default, means a new connection per request) and Vite proxies through a keep-alive agent, so a run no longer exhausts Windows' ephemeral ports. The specs that call the digest endpoint (`a11y-renewals`, `attention-renewals`) run in their own Playwright projects, one after the other, so they never replace each other's digest run; `e2e/axe.ts` runs axe in the light and the dark theme on every page it checks. It sets `LOGIN_THROTTLE_RATE=1000/min` for that test API only (the default stays `10/min`). It seeds with `seed_demo --accounts-only` (the specs assume an empty catalog). Digests in the suite go to Django's in-memory mail backend (`SOFTWARDEN_EMAIL_BACKEND`), and a test-only `POST /api/v1/e2e/run-digest` runs the digest and returns what was sent; it exists only when `SOFTWARDEN_E2E=1` and the database name ends in `_e2e`. Another test-only route, `POST /api/v1/e2e/multi-org-user` (Admin, same conditions), makes a second synthetic organization, "Fabrikam (synthetic)", and gives `multi@example.test` (demo password) an Editor membership in the caller's organization and in it, for the organization switcher spec (`e2e/org-switcher.spec.ts`). A third, `POST /api/v1/e2e/system-states` (Admin, same conditions), replaces the worker heartbeat and every schedule row with given states and can add sample failed and abandoned jobs, because the suite runs no worker (`e2e/system.spec.ts`). A fourth, `POST /api/v1/e2e/enterprise-org` (Admin, same conditions), makes a synthetic enterprise organization, "Northwind Enterprise (synthetic)", with `enterprise-admin@example.test` (demo password) as its only Admin and coordinator and its compliance profile off, so `e2e/compliance.spec.ts` can switch the profile on without changing the edition of the organization the rest of the suite shares. For the cloud journey, `POST /api/v1/e2e/outbox` (Admin, same conditions; `{to?, clear?}`) returns the in-memory outbox's mail (signup confirmations, invitations) and can take it out, `POST /api/v1/e2e/expire-impersonation` (any role of the member impersonated) ends the session's impersonation as its time limit would, and `POST /api/v1/e2e/run-export-jobs` (Admin; `{all?}`) runs queued organization exports now. `seed_demo --accounts-only` also makes `platform@example.test` (demo password), platform staff with no membership, on an `_e2e` database only (once: a rerun never grants it again); the full demo never does. Never run an e2e server where anyone else can reach it: its test-only routes let any Admin read every organization's mail and change other organizations. To reset your development database (for example after test records were written into it), stop the dev API and run `DROP DATABASE softwarden; CREATE DATABASE softwarden;` in `psql`, then `migrate` and `seed_demo`.

The first-run setup spec (`e2e/setup.spec.ts`) needs an installation with no accounts, so Playwright also starts a clean one (`e2e/setup-server.ts`): database `softwarden_setup_e2e` (recreated by `e2e_db.py` and migrated, never seeded), `bootstrap_admin --prepare` to write the one-time token to `apps/api/.bootstrap/e2e/setup-token` (git-ignored; the spec reads it there, as an operator on the host would), an API on port 8021, and Vite on port 5181 with its own dependency cache (`SOFTWARDEN_VITE_CACHE`).

### Cutting a release

A maintainer's steps; nothing is published until the tag is pushed. X.Y.Z below is the version.

1. **Prepare the release commit** on `main`:
   - in `CHANGELOG.md`, rename `## [Unreleased]` to `## [X.Y.Z] - <date>` and add a new empty `## [Unreleased]` above it. A release already written under its own heading (1.0.0 is) keeps the placeholder `unreleased (set on tag day)` until then: replace it with the tag day;
   - set `version` to X.Y.Z in `apps/api/pyproject.toml` (`/healthz/ops` and the OpenAPI schema read it from there), `mcp/pyproject.toml` and `apps/web/package.json`, `__version__` in `mcp/softwarden_mcp/__init__.py`, and `appVersion` in `deploy/helm/softwarden/Chart.yaml` (bump the chart's own `version` too when the chart changed);
   - refresh the lock files' own entries: `(cd apps/api && uv lock)`, `(cd mcp && uv lock)`, `(cd apps/web && npm install --package-lock-only)`;
   - run the gate (`apps/api/tests/test_upgrade_ci.py` fails when any of these versions differ from each other or from the newest CHANGELOG release, compared as PEP 440 versions so `1.1.0rc1` in uv.lock matches `1.1.0-rc.1`; INSTALL.md must pin the newest stable release, so leave it alone for a pre-release), commit and push.
2. **Wait for CI to be green on that commit**, including `migrate-from-previous` and `audit`: `gh run list --branch main --limit 1`, or the Actions tab.
3. **Tag and push the tag:** `git tag -a vX.Y.Z -m "Softwarden X.Y.Z"` then `git push origin vX.Y.Z`. Check the notes first with `bash ops/ci/changelog-section.sh X.Y.Z`; the workflow runs the same script.
4. **Watch the release workflow and approve it:** `gh run watch` (or the Actions tab, workflow "Release"). It runs Preflight (`ops/ci/release-preflight.sh`), the whole of `ci.yml` on the tagged commit, waits for approval on the `release` environment (Review deployments on the run's page), builds and attests both images by digest, starts them as a Compose stack (`/readyz` and `doctor` must pass), and only then tags them and creates the GitHub Release.

   A failure before Publish leaves only untagged digests in GHCR: nothing an installation pulls has moved. Fix the cause, delete the tag (`git push --delete origin vX.Y.Z`, then `git tag -d vX.Y.Z`) and tag again; the untagged digests can be deleted in the package settings.

   **A failure in Publish** is different: once `X.Y.Z` is on an image, that version is published and a re-run refuses it. Publish tags `X.Y.Z` on both images first, then `X.Y` and `latest`, then creates the Release, so finish the remaining steps by hand from the run's log and never retag a digest. The digests are in the run's `digest-softwarden` and `digest-softwarden-mcp` artifacts:
   - a missing version tag: `docker buildx imagetools create --tag ghcr.io/softwarden/<image>:X.Y.Z ghcr.io/softwarden/<image>@<digest>`;
   - a missing moving tag, only those the log's `Tags:` line lists: the same command with `--tag ghcr.io/softwarden/<image>:X.Y` and/or `:latest`;
   - a missing Release: `gh release create vX.Y.Z --verify-tag --title "Softwarden X.Y.Z" --notes-file notes.md`, with `bash ops/ci/changelog-section.sh X.Y.Z > notes.md` plus an "Images" list naming both tags and their digests (add `--latest=false` if `latest` wasn't in the `Tags:` line, `--prerelease` for a pre-release).

   Check each tag with `docker buildx imagetools inspect ghcr.io/softwarden/<image>:X.Y.Z` and `gh attestation verify`. A pre-release tag needs a CHANGELOG section of its own, headed with its full version (`## [1.1.0-rc.1] - <date>`).
5. **The first time only:** in the GitHub package settings (the organization › Packages › `softwarden` and `softwarden-mcp` › Package settings), link both packages to the repository and make them public. Check with `docker pull ghcr.io/softwarden/softwarden:X.Y.Z` from a machine that isn't signed in to ghcr.io, and `gh attestation verify oci://ghcr.io/softwarden/softwarden:X.Y.Z --owner Softwarden`.

From the first push to `main` after a tag, `migrate-from-previous` rehearses the upgrade from that release; before the first tag it skips.

### Live tests (real tenant, never in the default run)

Tests marked `live` (`apps/api/tests/test_live_entra.py`) call a real Microsoft tenant. They are skipped unless
pytest runs with `--live` **and** the credentials are in the environment, so the normal gate never reaches the network,
even on a machine where the variables are set. Run them only against a test tenant you are allowed to read (never a production tenant), with the discovery
app registration's read-only permissions consented (docs/PERMISSIONS.md):

```bash
cd apps/api
export SOFTWARDEN_LIVE_TENANT_ID=<tenant GUID> SOFTWARDEN_LIVE_CLIENT_ID=<application (client) ID>
export SOFTWARDEN_LIVE_CLIENT_SECRET=<client secret>   # read from your secret store; never commit it
# optional: SOFTWARDEN_LIVE_SUBSCRIPTION_ID (Reader on it) and SOFTWARDEN_LIVE_DATAVERSE_URL (an application user there)
uv run pytest --live -m live tests/test_live_entra.py -rs
```

They check the access check passes, that a run lists enterprise applications and registrations with credential expiry
(the app's own client secret), that Microsoft first-party apps are skipped and counted, that a second run reports
everything unchanged, that the license source reads, and, with the optional variables, Azure and Power Platform. They
only read, and they check the secret never appears in the runs, observations, audit events or logs. Two acceptance check steps
need a change in the tenant, made by hand on the dev tenant: rename an app registration and run again (the run counts
it changed and a dismissed candidate comes back), then delete it and run again (it shows as no longer seen).

The default gate has the other half of this check: `apps/api/tests/test_vendor_fixtures.py` replays responses in the
shapes each vendor documents (Graph, Azure Resource Manager, Power Platform, Okta, Google Workspace, Jira, ServiceNow,
Halo, and Entra and Okta ID tokens; `apps/api/tests/fixtures/vendors/`, with each file's source and provenance)
through the real clients and parsers. Run the live tests before each release.

## Run the full stack in Docker

`docker compose up -d --build` runs the whole installation with no `.env`: Caddy (`proxy`, the only published entry point, TLS on ports 80 and 443) in front of one image with the SPA and the API (`app`, gunicorn), a `worker` from the same image that fires the schedules (daily digest, discovery connectors, import purges) and runs queued jobs (PostgreSQL-backed, no broker), and PostgreSQL 17 (`db`). Before the database starts, the one-shot `init` service generates this installation's secrets into the `softwarden-secrets` volume (`apps/api/softwarden/init_secrets.py`): the Django secret key, the database password and the credential encryption key, each a 0600 file owned by the app user. Any of them set in the shell or in a `.env` file next to `compose.yaml` (git-ignored, optional) wins: `SOFTWARDEN_SECRET_KEY`, `POSTGRES_PASSWORD`, `SOFTWARDEN_CREDENTIAL_KEYS`. Migrations run in the one-shot `migrate` service, which `app` and `worker` wait for (`docker compose logs migrate` shows them). `scripts/setup.ps1` (Windows PowerShell 5.1 or PowerShell 7) and `scripts/setup.sh` (Linux, macOS) do the same with preflight checks: Docker and Compose v2, TLS interception on the network (see `ca-certs/README.md`), and free ports.

**First run.**

```bash
docker compose up -d --build                                   # or: scripts/setup.ps1, sh scripts/setup.sh
docker compose exec app python manage.py bootstrap_admin       # prints the one-time setup token
```

1. `bootstrap_admin` prints `Open https://localhost/setup and enter this one-time token within one hour:` and the token. The token is a private file in the `softwarden-bootstrap` volume, written at start-up by `bootstrap_admin --prepare`; no browser is ever shown it. After an hour, run the command again for a new one.
2. The first time it runs, it also prints the **credential encryption key** with instructions: back it up now, off this machine (a password manager). It is shown once; afterwards `bootstrap_admin` prints only its key id and how to read it again (`docker compose exec app cat /data/secrets/credential_keys`).
3. Open https://localhost/setup, accept the browser's certificate warning (Caddy's own local CA), and enter the token, the organization name and timezone, and the first Admin's email, name and password. The Admin is signed in and setup closes for good. Setup also closes the moment any organization or account is created another way (`bootstrap_admin --create`, `seed_demo`, Entra sign-in, a restore).

The setup page is public and lives outside the signed-in app. While setup is pending, a signed-out visitor to any address is sent there from the sign-in page. It asks for the token (surrounding whitespace is trimmed), the organization name, a timezone (defaulting to the browser's), and the Admin's name, email and password (12 characters or more, not a common one). It explains a refused token with the `bootstrap_admin` command and a rate limit with the wait, and once setup is done it shows that and links to sign-in. The API behind it is `GET /api/v1/setup` (`{"pending": true|false}`) and `POST /api/v1/setup` with `token`, `organization_name`, `timezone`, `email`, `name` and `password` (public, CSRF token required; 403 for a wrong or expired token, 409 once setup is done, 429 after five wrong tokens from one address in five minutes, counted per server process). To create the first Admin from the terminal instead: `docker compose exec -it app python manage.py bootstrap_admin --create` (prompts), or `--create --no-input --org-name ... --timezone ... --email ... --name ...` with the password in `BOOTSTRAP_ADMIN_PASSWORD`. Either refuses once setup is closed.

With the demo data (synthetic Contoso organization) instead of a real first organization, allow the simulated tenants
and hosts the demo's connector reads (`SOFTWARDEN_ALLOW_SIMULATED=1`, [docs/ENV.md](ENV.md); a real installation
leaves it off, and then refuses them):

```bash
printf '\nSOFTWARDEN_ALLOW_SIMULATED=1\n' >> .env   # app and worker read it; Compose reads .env by itself
docker compose up -d --build
docker compose exec app python manage.py seed_demo   # idempotent; closes first-run setup
```

In PowerShell, add the line `SOFTWARDEN_ALLOW_SIMULATED=1` to `.env` with an editor instead of the `printf`.

Without the flag `seed_demo` stops before writing anything and says to set it (`--accounts-only` needs no flag). The
dev stack (`compose.dev.yaml`) sets it already.

Sign in at https://localhost as `editor@example.test` (also `admin@example.test` and `viewer@example.test`) with the password `softwarden-demo-2026`.

**HTTPS.** Caddy serves `PUBLIC_HOSTNAME` (default `localhost`) with a certificate from its own local CA (`CADDY_TLS=internal`), kept in the `caddy-data` volume, so browsers warn until you trust that CA. Trusting it is opt-in only: `scripts/setup.ps1 -TrustLocalCA` or `sh scripts/setup.sh --trust-local-ca` says what it will change and asks first. For a real certificate, put `cert.pem` and `key.pem` in `./certs` (or `TLS_CERT_DIR`) and set `CADDY_TLS="/certs/cert.pem /certs/key.pem"` and `PUBLIC_HOSTNAME`. `HTTP_PORT` and `HTTPS_PORT` change the published ports (then also set `SOFTWARDEN_BASE_URL=https://host:port`); plain HTTP redirects to the HTTPS port. HSTS (one year) is sent only for a `PUBLIC_HOSTNAME` other than localhost, so trusting the local CA never pins local development ports to HTTPS. The app sends `X-Frame-Options: DENY`, the SPA's Content-Security-Policy (attachment downloads keep their own), `Permissions-Policy` (camera, microphone, geolocation off), `Cross-Origin-Opener-Policy: same-origin`, `nosniff` and `Referrer-Policy: same-origin` itself, so they hold behind any proxy (and HSTS when `SOFTWARDEN_HSTS_SECONDS` is set); Caddy sends the same policies where a response has none, and applies explicit server timeouts (headers 10 s, a whole request 5 min, a response 10 min, idle 2 min); `SECURITY.md` lists them with the rate limits and the upload checks, and says how to report a vulnerability. The app isn't published on the host, and it believes `X-Forwarded-For` and `X-Forwarded-Proto` only from the proxy (`SOFTWARDEN_TRUSTED_PROXIES`, default `proxy`; host names, addresses or CIDR ranges, `apps/api/core/middleware.py`). Stack defaults: `SOFTWARDEN_BASE_URL` and `SOFTWARDEN_CSRF_TRUSTED_ORIGINS` are `https://$PUBLIC_HOSTNAME`, `SOFTWARDEN_ALLOWED_HOSTS` is `$PUBLIC_HOSTNAME,127.0.0.1`, and cookies are Secure. For debugging, `docker compose -f compose.yaml -f compose.dev.yaml up -d` also publishes the app on http://127.0.0.1:8080 with non-Secure cookies, and the database on 127.0.0.1:5434 (`POSTGRES_PORT` changes it); the plain stack publishes neither.

**Credential encryption keys.** UI-entered secrets are encrypted under a keyring (`apps/api/core/credentials.py`): the keys in `SOFTWARDEN_CREDENTIAL_KEYS_FILE` (one per line; a path inside the containers, so mount the file into `app`, `worker` and `init`, for example from a `compose.override.yaml`) or `SOFTWARDEN_CREDENTIAL_KEYS` (comma-separated), newest first, or else the generated `credential_keys` file. The first key encrypts; every key decrypts. The legacy `SOFTWARDEN_SECRETS_KEY` still decrypts what it encrypted but never encrypts anything new. To rotate: `docker compose exec app python manage.py generate_credential_key` prints a new key (its key id on stderr); put it first in `SOFTWARDEN_CREDENTIAL_KEYS`, followed by the current key (`docker compose exec app cat /data/secrets/credential_keys`), and `docker compose up -d`; then `docker compose exec app python manage.py rotate_credential_keys` (try `--dry-run` first) re-encrypts every stored secret in one transaction and audits a count per organization. A secret no configured key opens is skipped and named (model, row, organization, slot and the page where it is entered again) while the rest move to the new key; add `--strict` to exit non-zero when that happens. Remove the old key only once no backup you might restore needs it. `rotate_secrets` is a deprecated alias. **Database backups don't include the key, and `docker compose down -v` deletes it with the volumes**: keep your copy off the server. `docker compose exec app python manage.py setup_status` prints `migrated`, `setup_pending` and `encrypted_secrets` (a count) for scripts. `manage.py doctor` gives the full picture. It prints one line per check (`OK`, `WARN` or `FAIL`, with a fix for anything not OK) and exits 1 on a failure, `--json` for scripts. It covers the database and migrations, first-run setup, the worker and schedules, the credential keys (and secrets stored under a key that is gone), the backup key and last backup, the base URL and TLS host name, email, and each organization's single sign-on and discovery connectors. It never prints a secret.

**Upgrading a stack from an early version without generated secrets.** Its database already exists with the password it was created with (`softwarden-dev` unless you set one), so the first `docker compose up` needs `POSTGRES_PASSWORD` once, in the shell or `.env`; `init` stops with that instruction otherwise, and then keeps the password in the secrets volume. Keep `SOFTWARDEN_SECRET_KEY` and `SOFTWARDEN_SECRETS_KEY` if you had set them (sessions and stored connector secrets keep working), and run `rotate_credential_keys` once to move connector secrets to the new key. An existing installation never reopens first-run setup. The app moves from http://localhost:8080 to https://localhost.

**Verify the stack.** `docker compose ps` shows `app` healthy, `worker` and `proxy` running and `init` exited (0); `curl -k https://localhost/healthz` and `/readyz` both answer 200 (`/readyz` answers 503 until the worker's first tick, a few seconds after `app` turns healthy); `docker compose logs worker` shows one `worker tick ...` line a minute; `docker compose exec worker python manage.py run_worker --once` prints one `Tick:` summary; `docker compose exec app python manage.py upgrade_check` ends with "All upgrade checks passed." `docker compose down` stops the stack and keeps the volumes; `down -v` deletes them, including the credential key.

Anyone who signs in with a password and forgot it can reset it themselves when the installation can send email (`SOFTWARDEN_SMTP_HOST`): `POST /api/v1/auth/password-reset {email}` emails a single-use link, good for an hour, and `POST /api/v1/auth/password-reset/confirm {token, password}` sets the new password and signs the account out everywhere (docs/API.md "Password reset by email"; platform staff and accounts that sign in only through single sign-on get no link). If an Admin is locked out, `docker compose exec app python manage.py reset_admin <email>` prints a temporary password (and reactivates the account if it was deactivated); they must change it at next sign-in. Both commands write audit events without the password. A user can belong to several organizations: an invitation to an email that already has an account adds it to this organization once that account accepts while signed in as itself, and `DELETE /api/v1/users/{id}` (Admin; no SPA control yet) takes them out of this organization only. An Admin can't reset the password of, deactivate, or unlink the Entra sign-in of an account that also belongs to another organization (that would change the shared account). Such a person recovers through the operator: `reset_admin --any-member <email>` resets any member, not only Admins, and the event is written in each of their organizations. A deactivated account that belongs to no organization is turned back on with `manage.py reactivate_account <email>`; it refuses an account with any membership.

**Editions.** Every organization has an edition: `community` (the default) or `cloud`; the field also accepts `enterprise`, a value reserved for a planned Enterprise edition. Features are switched on by capability names, listed with the edition mapping in [docs/CAPABILITIES.md](CAPABILITIES.md); `GET /api/v1/auth/me` returns the current organization's `edition` and `capabilities`, and a feature the edition lacks answers 403 with a problem naming the capability. Only an operator changes the edition: `docker compose exec app python manage.py set_edition --list` shows each organization's slug and edition, and `set_edition <org-slug> cloud` changes it (written to that organization's audit log). Every edition has every feature in this repository; the cloud edition adds what a hosted service needs. An organization set to the reserved `enterprise` has the community features, plus per-organization nightly backups, and the community limits.

**Platform admin console (cloud).** Whoever runs a hosted installation can see and support its organizations through `/api/v1/platform/`: every organization with its usage (refreshed hourly), edition changes, canceling a scheduled deletion, suspending, per-organization capability overrides and limits with an optional expiry, an export made on a customer's request, and impersonating a member (re-authentication, a reason, 30 minutes by default via `SOFTWARDEN_IMPERSONATION_MINUTES`, a banner in `auth/me`, and no credentials, tokens, secrets or deletion while impersonating). Platform staff are granted only with `docker compose exec app python manage.py platform_staff grant <email>` (`revoke`, `list`); staff status gives no role in any organization, and every platform action is audited in an installation-wide platform stream and in the organization's own audit log. In cloud mode (`SOFTWARDEN_PLATFORM_TOTP`) staff also need a code from an authenticator app (TOTP) for the console and for each impersonation; a lost device is reset with `platform_staff reset-second-factor <email> --reason ...`. See [the platform admin runbook](04-development/platform-admin-runbook.md). Cloud mode is not supported for production in 1.0; if you run it, keep `/platform` and `/api/v1/platform/` behind your own access proxy or VPN ([docs/CLOUD.md](CLOUD.md#not-supported-for-production-in-10)).
In the browser the console is at `/platform` (Platform console in the account menu), with signup at `/signup`, Usage and limits in the account menu, and export and deletion in Organization settings.

- `GET /api/v1/schema?format=json`: the OpenAPI description (signed-in users; see The REST API). Every endpoint is generated from its serializers, FilterSets and pagination, with RFC 9457 problem responses and If-Match on conditional writes: catalog, renewal and notification endpoints (records, AI agents, AI providers and models, integrations, relationships, reviews, instances, people, teams, departments, vendors, software categories, tags, saved filters, bulk edit and bulk delete, assessments, dependencies, Needs attention, snoozes, preferences, renewals and the digest log), and so are discovery, imports, API tokens, users, organization settings, the audit log, sign-in, setup and System. `manage.py spectacular --validate --fail-on-warn` reports no errors and no warnings (`tests/test_openapi.py` runs it).
- `GET /healthz`: the process is up (no database call).
- `GET /readyz`: the installation is ready. 503 unless the database answers, every migration is applied, the worker's heartbeat is under 180 s old, and no schedule is overdue (its due time passed more than 30 minutes ago) or stuck (a run's lease expired). A schedule whose last run failed is reported (`"schedules": "failing"`) but doesn't fail it. It is public, so it gives only the worst state (`ok`, `failing`, `overdue` or `stuck`; the worker `ok`, `stale` or `not running`), never a schedule's name or the heartbeat's age: those are on the System page and at `/healthz/ops`. The migration check is kept for 30 s per process. Before the worker's first tick it answers 503 with `"worker": "not running"`. Point an outside monitor here.
- `GET /readyz/web`: this web container can serve (database and migrations only). The container healthcheck uses it and the worker waits for it, so it must not depend on the worker.
- `GET /healthz/ops`: the operator health view: database latency, migrations pending, the worker heartbeat's age, schedules in a bad state, queued jobs and the oldest one's age per lane, jobs failed or abandoned in the last 24 h, the backup's age and state, disk space on the media (and, where mounted, backup) path, and the version. Send `Authorization: Bearer <ops token>` (the generated `ops_token`: `docker compose exec app cat /data/secrets/ops_token`, or set `SOFTWARDEN_OPS_TOKEN`), or, on an installation with exactly one organization, open it signed in as an Admin; anyone else gets a 404. No organization's data and no secrets. It answers 200 with a `status` (`ok`, `degraded`, `unhealthy`, `migrations_pending`) whenever the database answers, 503 when it doesn't; alert on `/readyz`. See [the operations note](04-development/operations.md).
- `GET /api/v1/setup` (public): whether first-run setup is open; `POST` creates the first organization and Admin with the one-time token (see First run). `GET /api/v1/auth/options` (public) carries the same answer as `setup_pending`, next to `entra`, so the sign-in page needs one request.
- `GET /api/v1/system` (Admin): the worker's heartbeat, each schedule's state (`ok`, `running`, `never_run`, `failing`, `overdue`, `stuck`, `disabled`), last start, finish, success, error and next due time, and job counts for this organization and for installation-wide jobs. Administration › System status shows it (`g y`), refreshed every 30 seconds while the page is open.

**Worker.** `run_worker` ticks once a minute: heartbeat, then each due schedule (build and send digests, discovery connectors, import purges every minute; deleting finished jobs older than 30 days nightly at 03:40 UTC), then queued jobs from the `core.Job` table, claimed with `SELECT ... FOR UPDATE SKIP LOCKED` under a lease. A failed job is retried after 1 and 4 minutes, then marked failed; a job whose lease expires (its worker died) is marked abandoned and not retried. Two workers can run side by side: each schedule fire and each job runs once. A schedule run holds a 5-minute lease that the worker renews while it runs (up to an hour), so a killed worker frees it within minutes. On SIGTERM the worker stops claiming and finishes the job in hand; compose gives it 90 s (`stop_grace_period`). A failing schedule records only the exception type (the System status is shared by every organization's Admins); the message is in the worker log. Apps register their schedules and job kinds in `core/jobs.py` from their `AppConfig.ready`. Job payloads carry record ids, never secrets (`enqueue` refuses secret-looking keys). To pause a schedule, set `enabled` off on its row (`core_schedule`); the worker never turns it back on.
- Logs are JSON lines on stdout (`docker compose logs app`), rotated by Docker at 10 MB × 5 files. Each line carries `request_id` (the `X-Request-ID` the response returns and the audit events record; the job's id inside a job), and `org` and `user` ids once known; the app writes one `softwarden.request` line per request with `method`, `path`, `status` and `duration_ms` (gunicorn's own access log is off). No line ever carries a query string, and configured secrets are replaced with `[redacted]`. Set `SOFTWARDEN_LOG_FORMAT=text` for plain lines when running locally. Optional OpenTelemetry trace export: build with `--build-arg WITH_OTEL=1` and set `OTEL_EXPORTER_OTLP_ENDPOINT` (the operations note).
- Compose already runs behind TLS (Caddy) with Secure cookies; for another host name set `PUBLIC_HOSTNAME` (the defaults for `SOFTWARDEN_ALLOWED_HOSTS`, `SOFTWARDEN_CSRF_TRUSTED_ORIGINS` and `SOFTWARDEN_BASE_URL` follow it).

## Seeding at scale and timing check

`seed_scale` builds a separate synthetic organization ("Scale Test (synthetic)") at the size the timing check below measures: 1,000 resources (600 applications, 400 components), 2,000 instances, 5,000 reviews, 50 users and people, plus teams, departments and vendors, with a mix of ownership gaps, lifecycles, archived records and review states. For the dependency screens it also adds 300 integrations and 2,000 relationships (about 180 of them `implements`, the rest `depends_on`, leaning towards a few hub records so there are long chains, wide fans and cycles) and some 1,600 link confirmations (current, past the interval, or for a link that has since changed). For renewals it adds 300 renewals with about 900 cycles (history included) covering 1,700 applications. For AI agents it adds 60 AI agents on 12 models from 4 providers (one to three models each, some with gaps). For the audit log it adds 50,000 synthetic audit events over two years (record edits with snapshots, instance and review events with their record as related target, link additions, sign-ins and exports, grouped by request id), which `nfr_timing` times as the log's first page, filtered pages, the next page, a record's History and one event's diff (each p95 < 300 ms). It bulk-inserts and skips per-row audit events, uses a fixed random seed, and refuses to run if the organization already has resources unless you pass `--reset`. `--scale 0.05` builds a small version.

```bash
cd apps/api
export SOFTWARDEN_DEBUG=1                            # development mode, in each terminal
uv run python manage.py seed_scale                  # or: seed_scale --reset
uv run python manage.py runserver 127.0.0.1:8010    # separate terminal
uv run python manage.py nfr_timing                  # add --strict to exit non-zero on FAIL
```

`report_timing` times the dashboard and the spend reports (every `by`, and the CSV export) in process, with Django's test client and no server: it first tops the scale organization up to `--contracts` synthetic contracts (default 1,500, two lines each: one at 60 %, one sharing the rest; three currencies, 120 vendors; bulk-inserted like `seed_scale`, so no audit events), ANALYZEs the application's tables (so the timings don't depend on whether autovacuum has caught up with the rows just inserted; `seed_scale` does the same when it finishes), then prints p50, p95 and max over `--samples` requests (default 40). `--strict` exits non-zero when a p95 reaches 300 ms. Run `seed_scale` first. It refuses unless exactly one organization has the scale organization's name and `admin@scale.example.test` is a member of it, and, with `SOFTWARDEN_DEBUG` off (a production setting), unless `--synthetic-only-i-understand` is passed.

```bash
uv run python manage.py report_timing --contracts 1500   # add --strict to exit non-zero at p95 >= 300 ms
```

Sign-in for the scale data: `admin@scale.example.test` / `softwarden-scale-2026` (also `editor01@...`, `viewer01@...`). `nfr_timing` signs in once, then sends 200 requests per endpoint with 10 concurrent workers to a running server (`--base-url`, `--requests` and `--workers` change this). It reports p50/p95 for the application list, component list, integration list, search, global search (`/search` with vendor and company names, a prefix and a typo), application detail, Needs attention (All) and the dependency explorer (the ten most linked records, both directions, depth All, retired and instances included), a new assessment (`POST /assessments` on the ten most linked records: it computes and saves a snapshot of up to about 1,200 nodes; `--assessments` sets how many, default 30, and this one check **writes** them into the scale organization) and reading those assessments back, the renewals list, the data-quality summary and rules (500 ms), records failing a data-quality check and the application list filtered and ordered by completeness (300 ms), and one digest run for the organization (built in process and sent through the in-memory mail backend, then removed). It passes at p95 < 300 ms (500 ms for Needs attention; the explorer and the renewals list; 1 s for a new assessment; 1.5 s for reading an assessment back, which has no stated target) and a digest run under 30 s. Numbers depend on your machine and on `runserver` being a single process; treat them as a regression check, not a capacity test. Before timing, make sure no other server listens on the port, and let sockets in TIME_WAIT drain between long runs on Windows.

## Third-party notices

The image carries `THIRD_PARTY_NOTICES`: every Python package in `uv export --no-dev` (the runtime set from
`apps/api/uv.lock`) and every production npm package in `apps/web/package-lock.json`, each with its version, declared
license, source and the license and notice texts it ships. The Dockerfile builds it:
`apps/web/scripts/third-party-notices.mjs` lists the npm packages in the web stage, and
`docker/third_party_notices.py` reads the Python packages from the image's own environment with `importlib.metadata`
and writes the file.

A package that `uv export` names but the image lacks fails the build, with one exception: a package whose environment
marker is false on Linux, such as `tzdata ; sys_platform == 'win32'`, is never installed in the image and is left out.
The script evaluates the marker with `packaging.markers` when it is installed and otherwise reads simple
`sys_platform`, `platform_system`, `implementation_name` and `os_name` comparisons itself (the image has no
`packaging`). A marker it can't read, or one that is true on Linux, doesn't excuse a missing package: the build fails.

The file is at `/app/THIRD_PARTY_NOTICES` in the image and is served at `/THIRD_PARTY_NOTICES.txt`. The Debian
packages of the base image keep their licenses under `/usr/share/doc/<package>/copyright`.

To read it from an image: `docker run --rm --entrypoint cat <image> /app/THIRD_PARTY_NOTICES`. To build it locally
without Docker:

```bash
cd apps/web && node scripts/third-party-notices.mjs . > npm.txt
cd ../api && uv export --frozen --no-dev --no-hashes --no-emit-project > req.txt
uv run python ../../docker/third_party_notices.py --requirements req.txt --npm ../web/npm.txt --out THIRD_PARTY_NOTICES.txt
```

## Layout

- `apps/api`: Django 5.2 + Django REST Framework, in apps: `core` (organizations, memberships, audit events, sign-in with OIDC, secrets, the worker, jobs and schedules, health), `catalog` (records, people, teams, vendors, links, reviews, assessments, tags, saved filters), `money` (renewals), `notify` (digest, Needs attention, snoozes), `discovery` (connectors, Entra, candidates), `imports` (CSV import and export), `api` (the `/api/v1/` root, API tokens). SAML and SCIM come from an optional `ee` package that isn't part of this repository (`softwarden/ee.py`). Tables keep their original `catalog_*` names. Writes go through `catalog/services.py` (organization scope, validation, audit); review state and gaps are derived in `catalog/state.py`. Every view takes its organization and role from `core/access.py`: an API token's own organization, else the session's current organization. The DRF layer's foundation is `core/drf.py`: each route declares its minimum role (`min_role(...)` or `public` on a function view, `role_policy` on a viewset), which is also what enforces it, and `tests/test_url_coverage.py` fails on a route without one; `TenantViewSet` scopes querysets to the organization, sends writes to service functions, and adds ETag / If-Match, keyset pagination, ordering and django-filter FilterSets. Catalog routes are viewsets (`catalog/viewsets.py` for records, integrations, relationships, reviews, instances and assessments; `directory_viewsets.py` for people, teams, departments and vendors; `curation_viewsets.py` for tags, saved filters and bulk edit; `account_viewsets.py` for users, organization settings and your password; `audit_viewsets.py` for the audit log and each record's History, whose names and summaries come from `audit_log.py`; `serializers.py`, `account_serializers.py`, `filters.py`), as are renewals (`money/viewsets.py`), snoozes and the digest log (`notify/viewsets.py`), connectors, runs, candidates and a record's discovery sources (`discovery/viewsets.py`), import sources and runs (`imports/viewsets.py`) and API tokens (`api/viewsets.py`); composite endpoints such as Needs attention, the dependency explorer, organization settings and System are `RoleAPIView`s with serializers. Sign-in, sign-out, `auth/me`, switching organization, the sign-in options, Entra start and callback, setup and health stay small function views, each with its role and serializers.
- `apps/web`: Vite + React + TypeScript single-page app with Tailwind CSS v4 and shadcn/ui components (`src/components/ui`), served from the same origin as the API. Screens live in feature folders (`src/features/{catalog,money,notify,discovery,imports,admin,dashboard,setup,auth}`); shared components stay in `src/components`, and `src/lib` holds the session, theme and TanStack Query helpers (`useApiQuery`, `useApiMutation`, query keys that are the exact API path plus its parameters). Every color, light and dark, comes from `src/design/tokens.json`, which `npm run tokens` (run before `dev` and `build`) turns into `src/design/tokens.css`; `npm run lint` checks it is current, that the listed contrast pairs pass, and that no color is written anywhere else in `src/`. The theme preference (System, Light, Dark) is kept in the browser and applied before first paint by `index.html`. Inter Variable is bundled from `@fontsource-variable/inter` (SIL OFL), so no font is fetched from the network.
- `mcp`: the MCP server (its own uv project and image; docs/MCP.md): `softwarden_mcp/client.py` (the REST client and how problem details read as tool errors), `tools.py` (the tools), `server.py` (stdio and authenticated streamable HTTP). Compose runs it only with `--profile mcp`.
- `site`: the softwarden.dev website and the published docs, a static Astro site on Node 22 that touches nothing else in the repository (its own [README](../site/README.md)). Build it with `cd site && npm ci && npm run build` (output in `site/dist/`; `npm run dev` serves it on port 4321). It renders `docs/*.md` and `CHANGELOG.md` at build time and fails the build on a doc link it can't resolve, so `.github/workflows/site.yml` builds it whenever `site/`, `docs/` or `CHANGELOG.md` changes. It isn't part of the image.
- `compose.yaml` and `Dockerfile`: PostgreSQL plus the web/API container. `softwarden/ops.py` has the health and readiness probes and the operator view `/healthz/ops`, and serves the built SPA; `softwarden/logs.py` formats JSON logs; `softwarden/otel.py` is the optional trace export.
- Audit payloads go through `catalog.services.audit`, which redacts secret-like keys and keeps Person names and emails out (Person ID only), and adds the target's before / after snapshots (`catalog/snapshots.py`, per-model whitelists), the related record and the request id (`core/request_context.py`).
